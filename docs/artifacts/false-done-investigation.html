Why the test said “It works” when nothing reached Drive

A full walk through this chat, from your first message to the last change, in plain words. Date of the work: 13 November 2026.

1. What went wrong

You recorded a workflow called Github to Drive Handoff. It does this: open GitHub, pick a .gitignore file, download it, then open Google Drive and upload that file.

You tested it in the Build Studio. The chat said “It works. Approve it when you’re happy.” But when you opened Drive yourself, the file was not there.

The core problem

The test lied. It reported success for something that did not happen. That is worse than a test that fails, because you would have approved and shipped a workflow that does not work.

You asked for three things: look into it deeply, start from first principles, and give one general fix for the whole system, not a patch that only helps this one GitHub-to-Drive recording.

That last rule shaped everything I did. Every change below is a rule that applies to any workflow on any website.

2. How a test works

When Conxa runs a workflow, it does not just click and hope. After each step it asks: “Did that really work?” It answers by collecting small pieces of evidence. I will call them checks.

Think of it like this

You post a parcel. A good courier does not only say “I handed it over.” They also check: was it signed for? Did the tracking update? Is it in the right house? Each is a separate piece of proof. The more separate, trustworthy proof, the more sure you can be.

The proof ladder

Conxa grades every step on four rungs. Each rung is a stronger claim than the one below it.

1. PerformedWe did the action. (We clicked or we set the file.)
2. AcceptedThe app took it. (The page reacted.)
3. CompletedThe work finished. (The upload bar ended.)
4. Result existsThe right thing is really there. (The file is in the list.)

Each check answers one of four things:

  • yes the evidence says it worked
  • no the evidence says it did not
  • can’t tell I could not read this evidence
  • not yet it is still working

A step counts as “proven” when enough separate checks say yes at a high enough rung. For an upload, the rule asked for the third rung, completed.

5. Why it said “Done”: four mistakes

Mistake 1. A witness that could never say “no”

The check c2 counted any success reply to any data-sending request. Drive and most big apps send small requests constantly: analytics, auto-save, “I’m still here” pings. They get a success reply whether or not your upload happened.

Analogy

A shop camera sees a customer walk in and you say “they bought something.” They might only have walked in. The camera would show the same thing either way, so it proves nothing about buying.

The “is the work running?” gate used the same background traffic as its sign that the upload had started. So that gate also said “done” for the wrong reason.

Mistake 2. Ignoring the thing the recording already told us

Your recording is the expected outcome: “after a real upload, you see upload complete.” When that message never shows up, that is evidence against the step. The engine treated it as nothing. A “no” from a check counted for no weight at all.

Mistake 3. A pop-up that was never seen was treated as fine

The step after the upload watches for pop-ups. Your recording only ever saw one version: the “1 upload complete” tray. In the test, that tray did not show. The engine found “no pop-up” and moved on as if that was a normal, healthy path. Nothing recorded such a path as normal.

Mistake 4. Missing the bigger pattern

In recent days, the fixes in this project went toward stopping false failures (tests that fail when they should pass). That is understandable, because failures are visible and annoying. But nothing pushed the other way against false successes, because a false success is quiet. Nobody notices it until the customer does.

The upload step runs. A file is “chosen.”
↓
Drive sends a background request. It gets a success reply.
↓
The engine takes that as proof. It ignores the missing “upload complete.”
↓
Step marked proven. The test says “It works.” No file is in Drive.

6. The damage it did afterwards

This was the part that worried me most. After a test passes, Conxa learns from it. It looks at which checks said yes and which said no, and then it “calibrates” the skill. A check that never said yes is marked dead and stops counting. This is a clever feature when the test is honest.

But this test was a false pass. So the learning went wrong. I read your saved skill and found:

  • c3, c4 and c5 were marked dead. c4 and c5 were checks you had confirmed in the chat.
  • c1 and c2 were marked trusted.
  • The number of witnesses needed was raised to 2, but the two trusted ones are the weakest checks.
The trap

The false pass turned off the very checks that would have caught the false pass. From then on, c1 plus c2 would always pass, however broken the upload was. The skill was blind to this failure for good. The test certified the checks that certified the test.

7. A second bug I found on the way

While reading the runtime log, I saw the same error 59 times: a0l is not defined.

What it means

Some small pieces of code have to run inside the web page, not inside Conxa. When the app is built for customers, most of its code is scrambled on purpose to protect it. The scrambling replaces words with codes, and it adds a small decoder (named like a0l) that lives in Conxa. A function that runs inside the web page cannot see that decoder. So it crashes.

I confirmed it in the built app: the check that makes sure the page is the right size and that clicks land where aimed started with const s=a0l. That check was crashing at the start of every step. Worse, the code that called it caught the error and treated it as “all fine.”

Same pattern again

A broken measuring tool that reports “fine” is another kind of false success. It did not cause your Drive problem, but it is the same disease: when an instrument breaks, it must not read as a pass.

The same flaw also hid in clipboard steps, in some page reads used by AI-driven spans, in a check that decides which pop-up button is safe to click, and in a check that asks if an upload field accepts many files. I fixed all of them the same way.

8. The plan I made before touching any code

I was in plan mode first, so I wrote a plan and you approved it. Before that I got a second opinion from a stronger reviewer model. Its main point, which I agreed with, was to split this into two separate problems:

You reported A (“it said success”), so A came first. I did not want to “fix” B on a hunch and then wrongly claim it was solved.

The likely guess for B: when you click “File upload” in Drive, Drive opens its own file picker window. Conxa’s engine throws that window away, then pushes the file into a hidden file box that it finds by guesswork. That would explain a missing upload. It is a guess until a live run shows it.

9. What I built

Five general rules. None of them mention GitHub, Drive or any website.

Change 1. A witness must be able to say “no”

Conxa now learns which background endpoints a page is already calling during the earlier steps of the same run. When the upload step runs, requests to those known background endpoints are marked as background noise. They no longer count as proof, and they no longer count as “the work started.”

Analogy

Before the parcel is posted, you note down the background noises in the room: the clock, the fridge, traffic. After you post, only a new sound counts as evidence of the parcel.

Change 2. The recording is the expected outcome

If every “the app says…” result from your recording is absent in the test, the step can no longer be proven by weaker evidence. Only something that looks for the result itself (like reopening the page and finding the file) can prove it. If that cannot, the step ends as “Couldn’t confirm.”

  • “Can’t tell” is not the same as absent. Only a real “no” counts.
  • If even one recorded result appears, the step is allowed. This avoids punishing a stray junk word, such as “maximized”.
  • Nothing pauses to ask a person, and no AI guesses. It is a fixed rule.

Change 3. A test cannot “learn” from a false pass

  • A test only teaches the skill when a check at the completed level or higher really said yes. A pass that rested on “the step ran” teaches nothing.
  • “Can’t tell” never turns a check off.
  • Checks from your recording, and checks you confirmed in chat, are only turned off by you, never by a test.
  • Every mark a test writes also records which checks proved it. A mark with no such record is ignored.

This last point fixes damage that already happened. Your skill had marks with no record, so it is repaired automatically, along with any other skill in the same state. I did not edit your skill by hand.

Change 4. A broken measuring tool cannot read as a pass

I moved every in-page function into one file, page_scripts.js, which is built in a way that keeps it working inside the page. I also added a guard script (check_page_eval_seam.js). It now fails the build if anyone adds an in-page function anywhere else. I tested the guard by planting a deliberate violation and checking that it complained. At first it did not complain because of a typing slip in my own code, which I then fixed. That is why that test was worth doing.

Change 5. “Must never pass” tests

I saved this run’s exact answers in a file (proof_must_not_pass.json) and wrote tests that demand: this evidence must never be judged proven. If someone loosens the rules again to stop false failures, these tests will fail first. Python and runtime tests were also added for the new rules.
