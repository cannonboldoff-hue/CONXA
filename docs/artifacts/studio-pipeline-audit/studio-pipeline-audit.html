Where the Studio loses answers and pays twice

A code audit of the path from "compile finished" to "ready to test", and of the chat engine that carries it. It lists what can break in production, what is done twice, and a plan to cut model calls and wait time without loosening any safety rule.

What was read: the compile flow handler, the question builder and its store, the description check, the chat engine and command router, the lifecycle, the Studio's model client, the cloud proxy client, and the reply-size and retry settings. Not covered: the runtime's step executor and recovery, the recorder, the compiler internals, and the renderer. Call counts and wait times are worked out from the code, not measured on a live account.

Model calls per action

Clicking a choice costs nothing, which is the design working. Typing, chatting and finishing a compile fan out into several calls, mostly one after another.

Timeouts that do not hold

Each call asks for a short timeout. The Studio's cloud client never waits less than 90 seconds per request, the cloud may spend up to 75 seconds per request trying providers, and the Studio retries a 502, 503 or 504 twice. So every short call shares the same real ceiling.

Redundancy to fold away

The same question, the same wording job, or the same plumbing exists in more than one place. Each copy is a place for behavior to drift.

"Which values change?" is asked four ways

  • The recorder's "Changes each run?" toggle
  • Chosen values (addresses, rows, clicked items)
  • Typed values, with the same title and body
  • After a failed test, per value
Fold into: one card grouped by kind. The recorder toggle pre-ticks rows instead of hiding them; the after-test version re-opens that card.

Popups have three question kinds

  • Decision popup (outcome fork)
  • Popup seen in other workflows (app map)
  • Small popup the recorder flagged
Fold into: one builder with a "source" field. Keep the three answer paths, since they map to different gated commands.

Popup titles are worded twice

  • One wording call per popup during question building
  • The batch wording call rewrites the same title again
Fold into: the batch call only, with the popup's button names as context.

Two keyword lists gate paid calls

  • "Looks like a command" list in the router
  • "Might want a change" list in the chat engine
Fold into: one list with a test table of real messages and the call each should trigger.

Four ways to call a model

  • Direct calls with ad hoc error handling
  • The older OpenAPI-style wrapper
  • The wording helper with cache and fallback
  • Recovery's own cache file
Fold into: one advisory call: task, payload, validator, fallback, optional cache. Every non-primary call uses it.

Two model replies per change request

  • The proposal call writes a reply that is thrown away
  • The streamed reply is then written from scratch
Fold into: ask the proposal call for proposals only, with a smaller output ceiling.

Target shape

Same rules as today: code builds every question, choice and edit; a model only labels meaning and writes words; nothing changes the workflow without a click. The change is order and count.

After a compile, today

  1. Description check (waits)
  2. Popup wording, one call per popup (waits)
  3. Find and rank questions
  4. Batch wording (waits)
  5. First question appears

Three or more calls in a row before anything shows. Test stays blocked the whole time.

After a compile, proposed

  1. Description check, 20 s overall deadline, then fallback
  2. Popup wording per popup
  3. Find and rank questions
  4. First question appears in template wording
  5. Batch wording in the background, cached, revises cards not yet answered

One call blocks, with a hard limit. Wording never delays a question.

A chat message, today

  1. Map to a card choice, then route as a command
  2. Proposal call, up to 3 rounds, reply discarded (waits)
  3. Streamed reply
  4. Draft check on every general Chat turn, unguarded
  5. Summary, while the chat stays locked

A chat message, proposed

  1. One classify call: choice, action, change request, or chat
  2. Streamed reply starts at once
  3. Proposals in parallel, proposals only; change card posts when ready
  4. Draft check every turn
  5. Save the reply first; summary runs after the lock is released

The reply is saved before anything optional runs, so no later failure can take it away.

Plan

Phase 1about a day

Stop losing work. Guard the two unguarded calls, save the reply before the draft check, pick one rule for which questions block Test, fix the reply timeout, run summaries outside the lock, cache the wording call, delete dead code.

Phase 2two to three days

Make answers safe to apply. Snapshot the workflow before an answer's edits and restore it on any failure; record applied answers so a retry or restart never applies one twice; lock the question file around each update; give post-compile calls a real deadline; rebuild missing questions after a restart; read the chat file once per lifecycle update.

F03 F04 F06 F14 F15 · tests: second edit fails, workflow equals the snapshot; retry after a crash applies once; dead cloud returns fallback questions within the deadline

Phase 3about a week

Fewer calls, faster first card. Drop per-popup wording, post the first question before rewording, stream the reply before proposals, merge the two routing calls and the two keyword lists, run the draft check only on request, merge the "which values change" cards and the popup builders.

F07 F08 F10 F11 F12 F13 F21 F22 · tests: a message table that pins which calls each sample triggers

Phase 4two to three days

One way to call a model. A single advisory call with validator, fallback and cache; one shared list of picture tasks for the Studio, the core package and the cloud router.
