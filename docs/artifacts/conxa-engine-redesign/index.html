Proposal · checked line by line against the code, 2026-11-06

Conxa Engine v2

The engine is strong in the middle and open at both ends. Recording and compiling are careful and deterministic. But what the customer's runs learn stops at a dashboard and never reaches the compiler, most model answers are checked without a record of what was dropped, and nothing checks that every kind of action is handled all the way through. v2 keeps the spine and adds six changes that close those gaps.

This version goes one level deeper. Each change now has its own section: what the code does today, with file and line; the exact data it adds; the order it runs in; what can go wrong; and how to build and test it. Reading the code also showed that four claims in the first version were wrong. Those are marked Correction where they appear.

What stays, what changes

Keep

The order: record, understand, ask, compile, test, publish, run. The rule that the model never writes element addresses. Zero tokens for a normal run. The margin gate in the resolver. Every invariant in CLAUDE.md.

Close

The path from field runs back to Studio. The silent model guards. The video dead end after ten minutes. The one-run approval and the all-at-once skill release.

Widen

A contract that every action kind is handled end to end, and one typed step for the fuzzy middle of a task, so the engine covers more than clean click paths.

One ledger for every model call

S–M

What the code does today

The understanding check already does this well, so C1 copies it instead of inventing a new design. It runs an answer through five named stages, counts each rule it applies, grades the result and allows one retry.

  • timeline_understanding.py:410STAGES = ("shape", "reference", "override", "backfill", "safety"). The comment says why: "a bad prompt shows up as a number instead of a silence".
  • timeline_understanding.py:413_log(report, stage, rule, example) counts one use of a rule and keeps the first example, cut to 60 characters with emails scrubbed.
  • timeline_understanding.py:761_grade() returns unusable, weak or ok from code alone. A weak answer gets one retry with the reasons.
  • workflow_semantics.py:124The second opinion's guard. Its docstring: "Drop everything that isn't trustworthy, silently". Each gate is a bare continue.
  • build.py:2155What the second opinion applied is saved under compile_report["second_opinion"]. What it dropped is not.

  • intent_router.py:85A chat intent that is not allowed right now becomes plain "chat". No count.

The shared helper

Lift _log, _count and STAGES out of the understanding check into one small module. Each guard keeps its own rules and only adds a _log call next to each drop. No guard changes what it keeps.

# conxa_compile/llm/ledger.py  (new, ~40 lines)
STAGES = ("shape", "reference", "override",
          "backfill", "safety")

def log(report, stage, rule, ref=""):
    """Count one use of rule. ref is an id
    (step_key, question id, candidate ref),
    never model text or page text."""

def count(report, stage, *rules) -> int: ...

def entry(task, prompt_version, report,
          grade="", attempts=1, ms=0) -> dict

Rule names for the second opinion

Each existing continue in _validate_findings becomes one named rule, so the count says which gate fired:

unknown_step_key · unknown_kind · settled_literal · bad_placeholder · name_collision · unobserved_optional · bad_phase · ungrounded_assertion · unobserved_noise · over_cap

Build order

  1. Move the helper out of the understanding check. Its tests must pass unchanged: the report is byte-identical.
  2. Add log calls to the second opinion and write compile_report["second_opinion"]["dropped"].
  3. Same for wording, intent router, change cards and re-target.
  4. Show the counts on Human Review: one line, rules on expand.
  5. Switch SKILL_MODEL_LEDGER=observe to retry only for calls that have a grade. Today that is the understanding check alone.

What holds, what to watch

  • No guard changes what it keeps, so a compile stays byte-identical when the pass applies nothing.
  • The example is always an id, never model or page text, so the ledger holds no customer data.
  • Tier B needs no runtime change: its override_rejected reasons are mapped to the same rule names in the cloud summary.
  • Watch cost: a retry doubles tokens for that call. One retry only, and only where a grade exists. See docs/cost_model.md.

Tests One test per guard: feed a crafted bad answer, assert the rule counts.

C2

Video analysis that survives a restart

S
CorrectionThe first version said the video call was "one request". It is a submit-and-poll job with backoff and a cache. C2 is smaller than proposed, and signals.py needs no change: the cache already lives there.

What the code does today

  • video_analysis_client.py:62–63Polls every 3 s, gives up after max_wait_s=600.
  • video_analysis_client.py:99_retrying() backs off 2 s, 4 s, 8 s up to 30 s on 502, 503, 504 or no network.
  • video_analysis_client.py:77–93A job lost to a cloud restart is resubmitted, at most twice, then VideoUnavailable.
  • track_a.py:16–24The answer is cached by the prepared video's fingerprint. Only a new recording or a changed blur setting reaches Pegasus.
  • understand_flow.py:120–130Four failure types end in _flow_video_failed with the actions retry_video and re_record.

So the gaps are three. The job id is held only in memory, so closing Studio mid-wait means uploading again. After 600 s nothing tries again on its own. And nothing records how many tries it took.

The job record

One file per session: sessions/<id>/video_job.json. Written on submit and on every state change.

{"fingerprint": "<prepared fingerprint>",
 "job_id": "vj_8f2c…",
 "state": "waiting_cloud",
 "attempts": 4,
 "first_try": "2026-11-06T10:02:11Z",
 "next_try":  "2026-11-06T10:14:00Z",
 "last_error": "503 from /video/analyze",
 "blocked_code": ""}

States polling · done · waiting_cloud · blocked · failed. A fingerprint that no longer matches the prepared video makes the record stale, and a fresh job starts.

The order it runs in

  1. Submit, then write the record with the job id.
  2. Poll as today. On success write done and go on to understanding.
  3. When the 600 s budget runs out, write waiting_cloud and a next_try: 1, 2, 5, 10, then every 30 minutes, for up to 24 hours. Then failed.
  4. On Studio start, look for records in polling or waiting_cloud. Poll the saved job id first. Upload again only if the cloud says the job is gone.
  5. The card reads "Waiting for the video service. Next try 10:14. You can close Studio." Retry now stays on it.

What holds

  • Pegasus stays required. The watching flag stays on while the job waits, so compile and test stay blocked.
  • VideoBlocked (quota, trial, signed out) is never retried on a timer. Retrying will not help, and the person has to act.
  • The cache key is unchanged, so a finished job is never paid for twice.

One open question

The client treats a lost job as a cloud restart. That means cloud jobs are held in memory. After a long wait the saved job id may be gone, and resuming costs a fresh upload anyway. If cloud restarts are frequent, storing jobs in Postgres would make resume cheap. That is a cloud change and is left out of the S estimate.

Tests Fake clock and fake client already exist in the constructor (sleep, clock). Test: budget out writes waiting_cloud; restart resumes the same job id; blocked never schedules.

C3

An action contract

S, then optional L
Change of planThe first version proposed one registry that both languages read, sized L. Most of the value comes from a contract test, which is small. Generating code from the registry can come later, or never.

What the code does today

  • events.py:10ActionKind: a strict list of 42 kinds the recorder may produce, from click to outcome_fork.
  • handlers.js:388The runtime's HANDLERS table. 15 entries inline, more added below it (tab_open, popup, dialog_accept and others).
  • handlers.js:58NOOP_STEP_TYPES: kinds that do nothing at run time, such as frame_enter.
  • handlers.js:1090Dispatch is a plain lookup: HANDLERS[step.type]. A missing type is found only when a customer runs it.
  • test_invariants.js:26–44The only cross-check: frame types are no-ops and tab types are not.
  • skill_package_builder_saved_skill.pySome kinds change name at build time. upload_intent becomes upload. Nothing lists these renames in one place.

The contract file

One JSON file in conxa-core, beside the models. It follows the pattern of decision_surface_cases.json, which already pins one shared truth for both runtime and compiler.

{"version": 1,
 "kinds": {
  "click":         {"step": "click",
                    "run": "handler",
                    "recovery": true},
  "upload_intent": {"step": "upload",
                    "run": "handler",
                    "recovery": true},
  "frame_enter":   {"step": "frame_enter",
                    "run": "noop",
                    "recovery": false},
  "dialog_appeared": {"step": null,
     "why": "evidence only, folded into a fork"},
  "focus":         {"step": null,
     "why": "legacy, dropped at compile"}
 }}

The two tests

  1. Python. The file's keys equal get_args(ActionKind). Every kind with a step compiles from a minimal fixture event to that step type. Every kind marked recovery: false gets no_recovery_block.
  2. Node. Every step with run: "handler" has an entry in HANDLERS. Every run: "noop" is in NOOP_STEP_TYPES. Every key in HANDLERS appears in the file, so a dead handler is caught too.

Adding a kind is then: add it to ActionKind, add one line to the file, and the tests say what else is missing.

Later, optional

Generate ActionKind and NOOP_STEP_TYPES from the file, and let the editor read which fields each step type allows. That is the L part. Do it only if new kinds keep arriving.

What holds

  • frame_enter and frame_exit keep no_recovery_block. The test now enforces it.
  • The iframe chain and the tab rule are untouched. The file says which step a kind becomes, not how it is resolved.
  • The first run of the test may fail. That is the point: it lists every kind the runtime cannot run today.
C4

A typed agent span

M

What the code does today

  • run.js:344–357ai_review throws a planned pause. The server checks the answer against output_schema and binds it as an input.
  • run.js:361, handover.jshandover pauses for a person (2FA, a CAPTCHA) and revalidates the page on resume.
  • failure_response.jsTier B lets an agent nominate one candidate. The runtime checks it and does the action itself.
  • patch_gate.pyrun_if is refused on ai_review, handover and forks, so an input can never skip a guard.

The span joins these three ideas: a planned pause like ai_review, placed by the author, where the agent nominates actions like in Tier B, and the runtime does each one.

The step

{"type": "agent_span",
 "key": "s14",
 "goal": "Open the invoice for {{invoice_number}}
          from the list",
 "allowed": ["click", "fill", "scroll"],
 "until": {"type": "text_present",
           "target": "Invoice {{invoice_number}}",
           "required": true},
 "budget": {"actions": 12, "seconds": 120},
 "on_budget": "fail"}

until takes only the text, URL and state types that the second opinion may already add. Never a raw selector. Without until the editor will not save the step.

The order it runs in

  1. The runtime checks until first. If it already holds, the span ends with zero actions.
  2. Otherwise it parks and returns the goal, the allowed actions, the budget left and an accessibility snapshot of the page.
  3. The MCP client nominates one action on one element.
  4. The runtime checks the action is allowed, the element is on the recorded host and tab, it is not a decision dialog, and its label does not look irreversible.
  5. It does the action, spends one unit of budget, and checks until again.
  6. It ends on success, or fails when the budget runs out.

Where it refuses

  • Scheduled runs and runs with no agent attached: fail closed, as the decision-popup rule does today.
  • Inside a loop or option body, and right before a destructive step: refused by patch_gate.
  • Any popup that asks for a decision: the span stops. It never answers one. fork.js::isDecisionDialog and isIrreversibleLabel are reused as-is.
  • Outside the recovery cascade, like ai_review. It never touches recovery_stage.js or retry_budget.js.

What it changes for the product

A skill with a span is no longer zero-token on every run. The manifest should say uses_agent: true so a vendor never promises otherwise. The tracker gets span_start, span_action and span_done with the action count, so the cost shows on the dashboard.

Depends on C3, so the new step type is in the contract from day one.

Tests A fake agent that nominates a disallowed action, a decision-dialog button and an off-host link. Each must be refused without spending budget.

The new cloud route

GET /api/v1/tracking/{workspace_id}/step-health?skill=<slug>. Pure counting over events already stored. Clerk-authenticated, same tier check as the drift queue.

{"skill": "create-invoice",
 "release": "14",
 "runs": 120,
 "steps": [
  {"step": 14, "ok_tier1": 79, "ok_tier2": 38,
   "tier_b": 2, "failed": 1,
   "median_margin": 0.11,
   "won_by": {"role_name": 36, "text": 2},
   "stable_hash_match": 0.97}]}

What Studio does with it

  1. A Health tab per workflow lists steps that needed help. Default threshold: more than 20 % of at least 10 runs.
  2. When one signal kind won most repairs, Studio proposes a patch that moves it ahead of the broken one in the step's identity_bundle and recompiles that step's selectors with selector_grammar.py.
  3. The patch goes through patch_gate, then the C6 replays, then a Confirm card. Nothing applies by itself.
  4. The new release goes to the first ring.

The honest limit

Telemetry may not carry page text, so it says which kind of signal worked, not the text it matched. Studio can only promote a signal the step already has. When the element itself changed (new label, new place), the Health tab says so and offers Human Edit re-target or a new recording. It cannot invent the fix.

What holds

  • The cloud does not compile. It returns counts.
  • No model writes a selector: the patch is a code reorder of signals the compiler made, and the grammar writes the strings.
  • The resolver's margin gate and fingerprint check still decide at run time.
  • A new route under /api/v1, per the route rule.

Ship in two steps First the read-only Health tab, which has no risk. Then the patch proposal, once C6 rings exist.

C6

Prove it, then release in rings

M
CorrectionThe first version said C6 "needs an install id". It exists in install_identity.js. Percentage rollout exists too, for runtime updates in manifest_manager.js. Skill releases can reuse both.

What the code does today

  • test_flow.py:495–506cmd_flow_approve needs one passing test card. The "up to three attempts" in the file header are auto-fix tries after a failure, not repeat proof.
  • test_flow.py:162A test can end previewed: it stopped at the guard before an irreversible step. Repeat replays can use this.
  • install_identity.js:8One id per install, in identity/install_id. Sent in phone-home (server.js:2618), not in tracker events.
  • manifest_manager.js:46rolloutBucket(installId, component): SHA-256 to a stable 0–99 bucket. decideUpdate uses it with minimum_versions and required.
  • skillpack_update_routes.pyDelta sync per group. No rollout: every install gets the newest release.
  • sync.js:42version_manager keeps the last few versions on disk, so going back is local.

Part A: proof before Approve

  1. Run 1 as today, with the guard on. The person decides at any irreversible step.
  2. Runs 2 and 3 run on their own and stop at the guard, ending previewed. Nothing irreversible is done twice.
  3. If the person gave a second value for an input on the test card, run 3 uses it. That field is optional. With no second value, run 3 repeats the recorded inputs.
  4. The card reports "3 of 3 passed. Step 7 needed help in 1 of 3." A step that needed help is a flaky step, and Approve says so.

Cost: about three times the test time. The sandbox caps recovery at the zero-token tiers, so the extra runs cost no model tokens unless AI is turned on for the test.

Part B: rings for skill releases

# release record, new field
"rollout": {"percent": 10,
            "started_at": "2026-11-06T12:00Z",
            "baseline": "13",
            "halt_below": 0.9}
  1. Sync sends the install id in a header. The route serves the new release only when rolloutBucket(id, "skill:" + slug) < percent.
  2. The cloud compares success (wf_ok over all runs, split by wfv) between the ring and the baseline.
  3. If the ring falls below halt_below times the baseline over at least 20 runs, promotion stops and the ring is served the baseline again.
  4. Otherwise the owner raises the percent, or it rises on a schedule.

What holds, what to check

  • The guard holds on every replay. Only run 1 can pass an irreversible step, and only with the person's say.
  • The install id is not a machine fingerprint and never enters tracker payloads; the success split uses the release version only.
  • To check before building: whether sync accepts moving back to an older release. Today versions only move forward, so halting may need the cloud to re-serve the baseline under a new version number.

Decisions for you

  • C4 changes the zero-token promise for any skill with a span. Mark such skills uses_agent: true in the manifest?
  • C4 in the Studio test. Should a span be tested by the Studio's own model through the metered proxy, as ai_review is, or only with a person driving?
