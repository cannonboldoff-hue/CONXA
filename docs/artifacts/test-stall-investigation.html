Conxa Build Studio · test run investigation

Why the Studio test froze for 210 seconds, and how to stop it happening again

A workflow that recorded fine failed on its test, never tried the AI repair step, and then went silent until a timer killed it. This page explains what we found, in plain words, with the evidence, and then proposes fixes that do not depend on any one website.

The short answer

Cause 1 · the click misses

The Studio test window shrinks the website to fit a small panel. The robot that clicks does not know about the shrink. It aims at one spot and the click lands about 39% further down and to the right, on the wrong element.

Cause 2 · the long silence

After a missed click, the checker waited the full “page load” time (60 seconds) for a page change that could never happen. It did that for several checks in a row, so the 210-second run timer ran out before anything else could happen.

Why “Tier B” never ran

Studio tests are locked to repair levels 1 and 2 on purpose. Tier B (the AI helper) is only available when an AI agent runs the workflow for a customer. The Dry Run switch does not change this.

What I changed

Test runs now shrink the page in a way that keeps clicks exact. The runtime now proves clicks land where aimed. Failure re-checks wait at most 3 seconds. All of this is in your working folder, not committed.

Where things stand right now

In my live test the fixed build clicked correctly in a 1400×900 window that used to fail, and ran from step 1 to step 9. You tell me it is still failing for you. I have not seen your failing run, so I cannot yet say whether it is the same cause. The section “If it is still failing” lists the quickest ways to find out, starting with whether your copy is really running the new code.

Root cause 1: clicks land in the wrong place

Think of the test window as a TV showing a 1280×720 website. If the TV is smaller than the picture, Studio shrinks the picture so it fits. When a person clicks on the shrunken picture, the browser works out the right spot. But the test robot does not click with a mouse. It sends the browser typed-in coordinates (“click at 122, 360”), and the browser takes those numbers literally as positions on the TV, not positions inside the shrunken picture.

The proof: the miss follows the window size

I sent the same mouse position while changing only the size of the Studio window. The miss grew and shrank with the window and vanished when the panel was big enough that no shrinking was needed.

Why it “worked yesterday”

This is my inference, not something I measured on the old runs. A big enough window means no shrinking, which means no miss. Earlier successful runs most likely had a larger panel. A recent layout change (more side panels in Studio) makes the panel smaller, so the same workflow now fails. The workflow did not break. The panel got smaller.

Why the safety check missed it

The runtime has a check called checkGeometry that runs before each step. It asked the page “how big are you?” and the page truthfully said “1280 by 720”. That was correct and still useless, because the page was drawn smaller and the click numbers were never converted. The check measured what the page believes, not whether a click lands.

Root cause 2: the long silence after a miss

A missed click should fail in a few seconds and say so. Instead, nothing was reported for four minutes. After the click timed out (4.5 s), the runtime asked “did it work anyway?” by running the step’s checks. One of them is “the web address changed” and it comes with a floor of 60 seconds, because normal page loads can be slow. The address could never change (nothing was clicked), so it waited the full 60 seconds. A second, optional check about the address waited another 60.

The same check was repeated before and after every repair attempt, so there was never time to reach the later repair steps. The run timer then cancelled everything and the screen said the page “never reached the expected state… inputs don’t match what the site returned”. That message is wrong. It hid the real first error, “click intercepted”.

Why Tier B (AI repair) never started

  • It is switched off in Studio tests on purpose. Studio sets the repair ceiling to level 2 (runtime_tool.py line 319, CONXA_MAX_RECOVERY_TIER=2). The reason in the code: a test should judge the compiled workflow on its own merits.
  • Tier B is not a function the runtime calls. It is a hand-over to the AI agent that is driving the workflow for the customer. In a Studio test there is no such agent.
  • Dry Run is unrelated. It controls whether AI credits can be spent, not which repair levels exist.
  • Even if it were on, it would have starved. Tier B only begins after levels 1 and 2 give up. Those never gave up, because of cause 2.

If it is still failing: how to find out why

A fix that works in one run can still fail on another machine state. These are ordered from most to least likely. Each one takes under a minute.

  1. Is the test running the new code? The Studio test uses a copy of the runtime that is rebuilt by hand. Check that the build is newer than your last edit: 
    type "%USERPROFILE%\.conxa-build-studio-dev\sandbox\.conxa\version.json"
    The app_version stamp (for example app-v0.0.0-local.20261111230746) must be later than the time of my edits. If not, run scripts\build-app-local.ps1.
  2. Was Studio restarted after the panel change? browser_panel.js belongs to the Electron app, not the runtime. It only loads when the app starts. Close every Studio window and start again with scripts\conxa.ps1 dev studio.
  3. Is it the same failure? Look at the last lines of %USERPROFILE%\.conxa-build-studio-dev\sandbox\data\logs\runtime.log. The old problem logged step_N_click_start and then nothing until execution_deadline_exceeded. A different failure will show a different last line. Send me those 40 lines.
  4. Is it a different recording? The Studio window I saw late in the session was a newer 12-step version (slug github-to-drive-handoff-ae9b464d, “Lean.gitignore”), not the 11-step one I first investigated. A new recording can fail at a different step for a different reason.
  5. Is the window very small? Between a certain size, the panel may be below the minimum height the runtime accepts (480 px). The runtime now stops with the message above instead of clicking wrongly.
  6. Is it the Drive step? In my large-window run, step 11 (the Drive upload) paused for the “can’t be undone” guard and then reported “couldn’t confirm the upload finished”. That is a separate behaviour from the freeze and is not fixed by anything above.

The general fixes (from first principles)

The two bugs are different, but they share a shape: the system trusted a number that something else was supposed to keep true, and when it was not true, nobody noticed for minutes. Fixing only the clicks would leave the silence. Fixing only the silence would leave wrong clicks that fail quickly instead. These principles apply to every workflow on every site.

1. Test the invariant you actually need, at the place where it matters

ProblemThe guard checked “the page says it is 1280×720”. What we need is “a click I send lands where I aimed”.
PrincipleEvery guard should measure the end result a step depends on, not a nearby number that usually goes with it.
DoKeep the click-calibration probe. Add the same style of probe for the other things a step relies on: scroll lands where asked, keyboard focus goes to the page, the screenshot matches the viewport. Run them once when a run starts and after any window or layout change.

2. One owner for the coordinate space, and no second way to scale

ProblemTwo parties each thought they owned “size”: the panel (shrink with scale) and Playwright (sends raw numbers). Neither knew the other’s assumption.
PrincipleShrinking the display must never change what the page believes about its own size or where input lands. Pick one transform, keep it in one file, and prove it with a test per kind of run.
DoLong term, stop shrinking at all for runs driven by the runtime: run the page at true size in a hidden or separate window and show a live picture of it in the panel. Then the page, the clicks and the screenshots always share one space, and the panel size becomes a pure display choice.

3. Every step owns a time budget, and everything inside it shares one clock

ProblemAct, settle, verify, repair stages and re-checks each had their own timeout. Added together, one failed step cost minutes. Only a run-wide timer stopped it.
PrincipleThe step is the unit of failure. Give it a deadline, hand out slices of it (act, check, repair), and when it runs out, fail the step with its first real cause.
DoIntroduce a step budget object passed to settle, verify and recovery. Waits read “time left in the step” instead of fixed constants. Reserve a slice for each repair tier so a slow early stage can never starve a later one (including Tier B where it exists). Advisory checks run in parallel and never block.

4. Report the first real error, not the last symptom

ProblemThe screen said “inputs don’t match”. The real first error (click intercepted) was recorded and then lost when the run timer fired.
PrincipleA failure message is built from the earliest failure on that step plus what was tried after it.
DoStore the step’s first error on the run state. When a timeout or cancel ends the run, the summary uses it and lists the repair stages that were attempted, in everyday words.

5. No silent states

ProblemFor four minutes the log said nothing. A hang and a slow-but-working run looked identical.
PrincipleAnything that can wait must say what it is waiting for and for how long.
DoEmit an event at the start of each stage (“checking the page”, “trying repair 2 of 4”) with its budget. Show it in the test card. Add a watchdog: if a step has produced no event for 20 seconds, say so.

6. Do not trust “did the action run?” flags that over-report

ProblemA click that timed out before being sent was marked “may have acted”, so extra safety checks ran as if something might have happened.
PrincipleRecord what is known: “never dispatched” (intercepted, not visible, detached) is different from “dispatched, result unknown”.
DoSplit the flag in two. “Never dispatched” skips the long outcome checks and goes straight to repair. This also makes repeating a click safer, because we know it never went out.

7. Test builds must be provably current

ProblemThe Studio test ran a hand-built copy of the runtime that was older than two fix commits, with no warning.
PrincipleA test of the code should refuse to run on code that is not the code.
DoStamp each build with the hash of the source files. At the start of a test, compare it to the current source and either rebuild or show “this test is using an older runtime”. In the dev lane, load the plain source instead of the obfuscated build.

8. A permanent contract test for the test panel itself

ProblemThe unit tests used fake pages, so they could not see a real window shrinking.
PrincipleThe most basic promise (“a click lands where aimed”) should be tested on the real panel at several window sizes.
DoKeep the probe scripts from this investigation (they live in the session scratchpad) as one automated check: launch Studio, open a test page at 3 window sizes, assert the offset factor is 1.000 each time. Run it in CI or before release.
