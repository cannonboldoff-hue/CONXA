Conxa sign-in checks

Is this app signed in? Studio and the runtime now answer it with one rule.

Check now, Check all and the recording gate ran one checker inside Build Studio, and the runtime, which runs your skills, ran its own. Since 2026-10-30 both follow the same rule in the same kind of browser. The sections below show what each side did before, and what changed.

What changed

One rule

  • The same checks in the same order on both sides: password box, sign-in word in the address, success page, sign-in button, then a comparison with what a signed-out visitor sees.
  • Anything unclear is "unverified" and counts as not signed in, on both sides.
  • A shared test file runs the rule in Python and JavaScript, so they cannot drift apart.

One kind of browser

  • One Chromium holding the merged sessions of every app in the group, one tab per app, stealth options on. Studio now checks the way a run does.
  • Check now on one app loads the whole group's sessions too.
  • Both sides open the app's login page.

One trust time

  • A "signed in" answer is trusted for 10 minutes on both sides. The runtime used 6 hours.
  • Check now and Check all still always re-check.
  • Apps whose login page is the site's home page are no longer wrongly marked expired.
Same code Check now = Check all = recording gate All three call check_app_session_sync in Python. The decision logic is identical.
Different code The runtime It uses _isAuthenticated in JavaScript. It opens a different page, follows different rules and keeps its answer for much longer.

When is the sign-in checked?

Every moment a check can happen, in Build Studio and in the runtime. Live check means a real browser opens the login page and applies the shared rule. No check means only a saved answer is read. Own rule means a different check, not the shared one.

The three Studio paths are not exactly alike

They share the decision. They differ in when they ask and what they do with the answer.

Check now

  • Checks one app, whenever you press it.
  • Always opens a real browser. Never reuses an earlier answer.
  • Updates that app's badge on the Group page.

Check all

  • Same as Check now, for every connected app at once.
  • Apps that were never connected are skipped.
  • Updates every badge on the Group page.

Recording gate

  • Runs when you start a recording.
  • Skips any app checked in the last 10 minutes and trusts that result.
  • Blocks the recording if any app is never connected, expired or unconfirmed.

When the two could disagree (now fixed)

These come from reading the old code. I did not reproduce them in a live run.

Different page App with a success page

Studio opens the dashboard. Runtime opens the login page. A dead session can look different on each, so the verdicts can differ.

Different browser Shared sign-in cookie

Studio loads only this app's session. Runtime loads every app's session together, so a shared single-sign-on cookie from another app can make this one look signed in.

Different patience Slow page

A page that takes 12 s to load can leave Studio at "unverified" (10 s limit), while Runtime (30 s limit) waits and may say signed in.

Different memory Signed out elsewhere

If the site ends your session on its side, Studio can notice within 10 minutes. Runtime may trust its saved "signed in" for up to 6 hours.

Different sign-in signs Sign-in button, no password box

Studio reads a visible "Sign in" button as signed out. Runtime does not look for it and relies on the address and the clean-browser comparison.

How they were made to agree

The two sides cannot be literally one file, because Studio is Python and the runtime is JavaScript. Option A was built.

Built

A. Same rules, same tests

  • Make the generic path use the same page, same signed-out signs and same three answers on both sides.
  • Add a shared test file for the generic path, like the one the learned path already has.
  • Smaller change. Keeps Studio fast and independent of the runtime version.

B. Studio calls the real runtime

  • Studio would launch the runtime it already stages in its sandbox and ask it to run the check.
  • Literally one implementation.
  • Heavier: every Check all starts the runtime, and Studio depends on the runtime's version.
