Plain-language guide · Checking that work really got done

Proof of Done

Clicking Upload doesn't mean the file arrived. This guide explains how CONXA can make sure every step in a workflow really worked, on any website.

The big idea

Imagine you hand a parcel in at the post office. Handing it over doesn't mean your friend has it. The clerk still has to accept it, the van has to deliver it, and it has to be the right parcel on the right doorstep.

CONXA has the same problem. In your GitHub → Google Drive workflow, the last step was "upload the file". The step can look finished when the button has only been pressed. The file might still be on its way, or it might never arrive.

The problemToday a step passes if the page changed and nothing looked wrong. Neither of those shows the file arrived.
The ideaEvery step gets a short checklist: what should be true afterwards, what would prove it, and what to do if no proof comes.
The biggest change"I couldn't tell" becomes its own answer. Today, not being able to check often counts as success.
Fix this firstThe new upload check mistakes Drive's upload window for a question, and stops waiting almost at once.

A few words used in this guide

Step or action. One thing the workflow does, such as a click or an upload.
Check. One small test of whether something is true.
"Before" photo. A quick note of how things looked just before the action, so we can spot what changed.
Server. The company's computer behind a website. It's where your file ends up.
Evidence. Any fact that helps show what really happened.
Witness. A separate source of evidence, like a person who saw an event for themselves.
Warning. Evidence that something went wrong, such as an error message.
Run. One time the whole workflow is carried out.

The journey of an action

Every action goes through the same five stages and ends in one of six next moves. Only the checklist changes from step to step.

Next moveWhat it meansIn the parcel story
ContinueIt's proven. Move to the next step.Your friend confirms it arrived.
WaitThe app is clearly still working.Tracking shows the van is moving.
RetryDo it again, because we know nothing happened the first time.The post office confirms they never took it.
RecoverThe button moved or the page changed, so find it and try another way.The counter moved to another desk.
HandoverAsk a person, because only they can tell or decide.Call your friend and ask.
FailStop and say clearly what happened.The parcel was returned as refused.

How it can wrongly say success

A problem found while writing this guide. Google Drive's upload window has three buttons: Minimize, Close and Cancel all. The new finish check treats any window with several buttons like these as a question for a person. It then stops waiting and lets the step pass. Tested with those exact buttons, it gave up in 3 thousandths of a second, while the upload would still be running. The automatic test missed this because its pretend window had no buttons.

We ran the real finish check against 17 made-up situations, including ones chosen to trip it up, so this isn't a measure of how often it fails. The web pages were simulated, not the real Google Drive.

The time limits don't match each other

The upload wait can last 5 minutes. But the whole run has to end by 3.5 minutes, and Claude Desktop stops listening at about 4 minutes. So on a slow upload, the real answer may arrive when nobody is listening.

Four levels of proof

Today one word, "passed", covers four very different claims. Each needs its own proof, and a higher level can be false even when the lower ones are true.

Level 1

Performed

Did we do it?

We clicked the right button or chose the right file.

You handed the parcel over the counter.

Level 2

Accepted

Did the app take it?

The app reacted to what we did. A progress window opened or the server replied.

The clerk scanned it and gave you a receipt.

Level 3

Completed

Did the work finish?

The app says its work has ended. The last piece was sent or the job finished.

Tracking says "Delivered".

Level 4

Result exists

Is the right thing really there?

We can find the actual result, and it's the one we meant. The folder lists this exact file, and it's new.

Your friend has it, and it's your parcel.

Three simple rules stop us fooling ourselves:

  • It must be new. Only what changed since the "before" photo counts. A file with the same name that was already there proves nothing.
  • It must be the right thing. "A file appeared" isn't enough. It has to be the file this run was asked to upload.
  • The check must be able to tell the difference. If a check was already true before we acted, it can't prove anything. It counts as "can't tell".

The new design

The design adds two main things and keeps what already works.

  • A proof checklist for each step. It's made once, when the workflow is built.
  • An evidence notebook. It opens just before each action and notes everything that happens, on every tab.

What a checklist looks like

Step
Upload the file to Drive
What should be true
This file is in the folder and it's new
Level needed
Level 4, Result exists
Proof
The server says it has the whole file, and the folder lists this file name with one more file than before
Warnings to watch for
Any new error message or refusal
How long to wait
As long as progress keeps moving. If it stops for 45 seconds, stop waiting
If no proof comes
Ask a person. If nobody is there, report "couldn't confirm"

Workflows that are already published keep working. Their existing checks simply count as Level 2.

Rules that never change

  • The notebook opens before the action, so nothing gets missed.
  • Every check gives one of four answers: yes, no, not yet, or can't tell.
  • Checking only looks. It never clicks, answers a pop-up or repeats an action.
  • A run succeeds because its steps were proven, never just because it reached the end.
  • What's on the page stays on the customer's computer. Only pass or fail results are sent.
  • AI never decides what to click, and never makes the final decision about success.

Making and placing checks

Nobody has to write these checks by hand. They come from what happened during the recording.

  1. Watch. The recorder keeps watching after an action until things calm down. If you sat and watched a progress window until it said "complete", that's useful evidence.
  2. Name the goal. The system works out what kind of action this was, such as uploading a file or deleting something. There are about ten kinds.
  3. Find proof. Everything it saw becomes a possible check. Things that change every run, such as dates, are generalized. Things that match your input, such as the file name, are linked to it.
  4. Pick checks. Riskier steps get stronger proof. Every step also watches for warnings.
  5. Explain and confirm. Chat tells you in plain words: "I'll call this finished when the file name shows in the folder." You can agree or correct it.
  6. Test. In the Test run, each check must be false before the step and true after. Any that fail are removed.
  7. Publish rule. A step that can't be undone can't be published without real proof.

One check or several?

One check is enough when all three of these are true:

  • It looks directly at the result.
  • Our action is the only likely cause.
  • Being wrong would be cheap to fix.

Typing in a box and reading the box back passes all three. Anything else needs a second, separate witness.

Type of stepExamplesProof neededWitnessesIf there's no proof

Why two checks can still be one witness

Think of two friends telling you the parcel arrived. If both only read the same tracking page, you really have one source. If one read the tracking page and the other is standing next to the parcel, you have two.

On a website, a "complete" message and a new row in the list both come from the same screen. Some apps update the screen before the server has really finished, so both could be wrong together.

Working on any website

Writing special rules for Google Drive would fix one site and break on the next. So the differences are kept in four layers of information, and the program itself never mentions a website by name.

1. Works everywhereBasic signs on any website: was something sent, did it finish, is there a new error.From day one
2. Kinds of actionAbout ten kinds, such as "upload" or "delete". Each one says how much proof it needs.Shared list
3. What we learned about this appHow this app shows progress and success, in its own language. Layout only, never your data.Learned per app
4. This exact stepThis step's buttons, its inputs, and your answer about what "done" means.This workflow

Layer 3 also fixes the language problem. Words like "uploading" and "failed" no longer need to be English, because the system learns the words that app really used.

The most important rule is about repeating. Doing something twice could send an email twice or upload a file twice. So a step is only repeated when we have proof that the first try did nothing.

What can still go wrong

No checker can be perfect. It can only see what the app shows, and the app can be wrong. The goal is that when something can't be known, the person hears "couldn't confirm" and not a false "done".

Three choices that are yours to make

  • Should CONXA be allowed to reload or search a page to double-check? We suggest only when the workflow's author has approved it, because even looking can sometimes change things.
  • Should recordings keep a summary of the app's server messages? We suggest yes, keeping only the type and general address of each message, and never what's inside. This makes much better checks possible.
  • What should happen when an upload takes longer than the time limit? We suggest pausing the run and picking it up later, rather than making the limit longer.
