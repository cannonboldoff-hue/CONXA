How Conxa asks its questions

When a recording finishes compiling, Conxa checks the result against what you said the task was for, then asks only about the things it cannot know. This page shows every point where an AI model is used, what it is allowed to do there, and how the chat that carries it all works.

CodeOrdinary program rules. Same input, same result, every time. Code makes every decision that changes your workflow.
ModelAn AI language model, reached through the Conxa cloud. It reads meaning and writes words. It is never trusted to change anything by itself.
YouThe person building the workflow. Your clicks and answers are the only things that approve a change.

The short version

1. Check

One model reads your description next to the compiled steps. It says what looks the same on every run and what looks different, and whether the steps reach the goal you described.

2. Find

Code scans the workflow for 16 kinds of spot that deserve a question, such as a file path, a popup, or a step that cannot be undone. No model chooses what to ask.

3. Word

A second model call rewrites the draft questions in plain language. Code checks the result and keeps the original wording wherever the rewrite looks wrong.

4. Apply

When you answer, code turns your choice into an edit using the same gated commands you would use by hand. The model never touches it.

1. The whole journey

A workflow goes through eight stages. Most of them need no model at all. The orange pills show every model call that can happen at each stage.

2. After the compile, step by step

This is the part you asked about: how the result is checked against your description, and how the questions get written. Read it top to bottom.

What "check against the description" really means

Your description is the sentence you typed when you created the workflow, such as "download the .gitignore file for a repository". Conxa gives that sentence to the model next to the compiled steps and asks two things.

  • Does it cover the goal? The model says "no" only when your sentence clearly asks for an outcome the steps never reach. For example, you said "send" but the steps stop at "save draft". It then writes one short sentence, and Conxa asks you "Does this cover everything you wanted?"
  • Which recorded values were only true of that one recording? You clicked a repository called asia. Did you mean that one forever, or any repository? The model labels each value fixed, varies or unsure. "Varies" boxes arrive already ticked. "Unsure" ones arrive unticked. "Fixed" ones are not asked about at all.

If the model fails, Conxa does not stop. It asks about the likely values with every box unticked, so you stay in control. If you wrote no description, it asks nothing about meaning, because there is nothing to compare against.

3. Who decides what

Each row is one kind of question. Each column is one job. A square means plain code does that job. A circle means a model is involved. The two right-hand columns are all squares, which is the point: a model can help find a problem and phrase it, but it can never offer a choice or change your workflow.

The four fences around every model

It cannot pick an element.No model writes a selector, the address that finds a button on a page. A separate rules engine does that on the main compile path.
It cannot invent a choice.Choices and the edit behind each are fixed in code. A reworded choice is checked and falls back to the original if anything looks off.
It cannot skip your approval.Risky edits, such as always clicking "Replace", wait for you. Popups that ask for a decision are never answered on your behalf.
It cannot block you.Every call is advisory. A failed call means a plain template question, never a failed compile.

4. How much a model may write

Each task has a ceiling on how long its reply can be. A short ceiling is a safety feature: a model asked for a yes/no label has no room to wander. These are limits, not typical sizes.

5. How the harness works

The harness is the engine behind every chat, both the general Chat and each workflow's own conversation. It is one loop that handles one message at a time. Its guiding idea: try code first, and only reach for a model when code cannot tell what you meant.

The stage decides what chat can do

Next to the loop sits a small state tracker called the lifecycle. At any moment it holds a list of actions that are allowed: record, compile, test, publish, and so on. While a question is open, a compile is running, or a change card is waiting for you, "test" simply is not on the list. Chat can only choose from that list, and a message like "run it now" while a question is open is turned away by the server, not just hidden by the screen.

Anything with a side effect, such as starting a test run, posts a confirm card first and does nothing until you press the button. Inputs you state in chat ("test it with the repo asia") only pre-fill that card.

6. Every model call, in one table

Every call goes through one shared client. The Studio sends it to the Conxa cloud, which picks a provider from a pool and counts usage against your plan. Tasks that look at pictures are sent to a vision model.

Where to look in the code

  • conxa-builder/python/handlers/compile_flow.py: runs everything in section 2, in order.
  • conxa_compile/conversation/understanding.py: the description check and its fallbacks.
  • conxa_compile/conversation/clarify.py: finds the questions, validates rewording, turns answers into edits.
  • conxa_compile/llm/clarify_question_copy.py and fork_question_copy.py: the two rewording calls.
  • conxa_compile/conversation/harness.py and intent_router.py: the chat loop and command router.
  • packages/conxa-core/conxa_core/llm/client.py: every prompt, and every reply-size ceiling.
