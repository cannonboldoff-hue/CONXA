Build Studio Chat Copilot

Every workflow in Build Studio has one conversation next to it. You type, or press a button on a card, and the chat either does something, asks you something, or answers. This page shows what happens to one message, step by step, and why the model is never the one who decides what is allowed to happen.

Code decides A model is asked (advice only) You decide Saved on disk

The idea in four lines

One thread per workflowPlus a General Chat for talking before a workflow exists. Both are saved as a list of lines that is only ever added to.
Cheapest check firstA button press or a known phrase costs no model call. The model is asked only when code cannot tell what you meant.
The model proposes, code disposesEvery suggested edit passes three code gates before you can even see it. A suggestion that fails is dropped.
Nothing happens behind your backAnything with a side effect waits for a Confirm or Apply press. Every applied change can be undone.

Follow one message

Each message falls down a ladder of questions. The first rung that can handle it takes it, and everything below is skipped. Pick an example to light up its path.

What each kind of message costs

Every model call goes through the Conxa cloud and counts as an AI credit. Most things you do in chat cost nothing. Asking for a change costs the most, because a model has to look, propose and then explain.

When you ask for a change

This is the “copilot” part. A message that could ask for an edit goes through a pipeline where the model only suggests, code checks, and you press the button. The reply is written after the checks, so it describes only what is really on offer.

What the three gates allow

  • ① Field patch. Only fields that change meaning: typed value, input binding, intent, description, checks, consequence, branch timeout, loop limits, hover chain, review and hand-over settings. Never a selector, target or identity. Tested with the same validator Human Edit uses.
  • ② Popup step. Built from a popup actually seen during a test run, using the shared “try dismiss” builder.
  • ③ Structural. Insert, delete or move a step; set run inputs; replace text; turn a recorded value into a run input. Each one needs evidence from the workflow. A new click-type step can only borrow the identity of a step that already exists, and code does the copying.

What the model can look up

While diagnosing, the model may ask for more detail, at most twice. It gets text back, never a tool call into your workflow:

  • expand_step full detail of one step
  • get_step_screenshot the picture for a step
  • get_failure_evidence what the last test saw
  • get_edit_history what was already changed
  • list_workflows the other workflows

What chat is allowed to do right now

The workflow's stage decides which actions exist. Chat can only pick from that list, and a button, a stale confirm card or a typed command all get re-checked against it on the server. So “test it” does nothing while a compile is running.

While a typed message is still being answered, Test it and Approve are removed. A change card may be about to arrive, and you should not test or approve the version it would change. The project docs add the same hold while a question is open or a compile is running.
Actions that cost something or change things (record, discard, compile, test, fix, approve) post a Confirm card first. The reply says “nothing has happened yet”. Even then, “Test it” only opens a test card with your inputs pre-filled; you still press Run.

What the model gets to see

The cloud service keeps no memory between calls, so Studio rebuilds the whole picture every turn within a fixed budget: about 12,000 tokens in a workflow thread and 6,000 in General Chat. When it does not all fit, the lowest rows go first. Rows 1 to 4 are never dropped.

1Where the workflow is and which cards are waiting on you, with the choices on each.never dropped
2Pinned facts. What you said the workflow is for, every question you answered, the run inputs, steps that can't be undone, review points.never dropped
3Your latest message.never dropped
4The rules and the list of things it may propose. These sit outside the budgeted text.never dropped
5Workflow digest. Gets at most 60% of what is left. Shrunk piece by piece before any step is dropped; the model can ask for one step in full.shrunk first
6Latest test failure and its evidence.next to go
7Summary of older turns. Once 6 or more turns no longer fit, one extra call folds them into a summary of about 180 words.next to go
8Recent turns word for word, newest kept first, oldest trimmed first.trimmed first

Not drawn to scale: the rows are in priority order, not size. General Chat sees less, read-only: your groups and the apps they sign in to, your workflows and where each one stands, and which apps Studio has learned a map of. It cannot propose edits.

Fix it: the copilot acting on its own

After a failed test you can ask Studio to fix it. It runs the same propose-and-check pipeline in a loop, but applies each change itself and re-tests. It stops after three attempts and hands the decision back to you.

What the model cannot do

The model never

  • writes a selector or touches a step's target or identity
  • picks an action the workflow does not allow right now
  • runs anything with a side effect without your Confirm
  • applies half a change: edits go in together or not at all
  • answers a question card for you when its words are unclear: the card stays open
  • decides what a failed gate means: the proposal is simply gone

Code always

  • writes the one-line summary on a change card, from the checked fields
  • finds the step again by key when you press Apply, and refuses if it is gone
  • keeps one undo entry per card, and refuses Undo if the workflow moved on
  • saves your message the moment you send it, even if the model then fails
  • turns an out-of-credits or offline error into an error card with Retry
  • runs one turn at a time per thread; Cancel stops the stream and saves nothing half-done
