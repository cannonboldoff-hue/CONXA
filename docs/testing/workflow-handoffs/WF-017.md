## Root causes and decisions (engineering owner, 2026-11-22)

**17.4 / F1: second account sees the first account's work (S0 per spec). Needs an OWNER DECISION.**
- Root cause: this follows the current design. Studio is "single-tenant per install" (`packages/conxa-core/conxa_core/storage/skill_pack_store.py:6`). Every local workflow, group and saved sign-in is stamped `LOCAL_WORKSPACE_ID = "wrk_local"` (`conxa_core/workspace.py:12`, `workflow_store.py:70`, `group_store.py:144`). Nothing local records which Clerk account made it. `handlers/session.py:295-300` (`cmd_login` / `cmd_logout`) only touch the keyring. No doc (TRD, App-Flow, UI-UX-Brief, Auth-and-Updater) says what happens on an account switch.
- Why it is a real leak and not only cosmetic: publish takes the cloud workspace from the signed-in token (cloud `workspace_id` = Clerk `org_id` or `personal_<user_id>`, TRD §Principal). `cmd_publish_skill_pack` (`handlers/workflows.py:802`) and `cmd_build_installer` (`:941`) never compare the local owner with the signed-in workspace. So account B can publish account A's workflows into B's company, and can test with A's saved target-site sign-ins. That crosses the "workspace_id is the only identity key" invariant at the publish boundary.
- Options:
  - **A. Owner stamp + switch notice + publish guard (recommended, small).** On the first sign-in, write `data_dir/owner.json` = `{workspace_id, user_id, email}`, using the cloud's own rule (`org_id` or `personal_<user_id>`). On a later sign-in with a different workspace, `login`/`whoami` return `owner_mismatch: {email}`. The renderer then shows one plain card: "This computer has work from another account (a@x.com). It stays on this computer. Publishing and installers are paused until you choose." There are two choices. **Keep it for this account** rewrites the stamp, so the person takes over the work on purpose. **Put it away** renames `data/` to `data.<old-workspace>.<date>/`, nothing is deleted, and Studio restarts the backend. Publish and Build Installer refuse with `account_mismatch` until the person chooses. Trade-off: the first account's work stays visible until a choice is made. It meets "nothing leaks into another company" but not the spec's literal "nothing shows anywhere".
  - **B. Per-account data folder.** `settings.data_dir` becomes `data/<workspace>/`. This fully meets the spec, but it is a large change: `config.py` and every store, runtime test installs, plus a migration of the existing `data/`. It is not surgical. Only worth it if two people sharing one Windows login is a real customer case.
  - **C. Clear on sign-out.** This destroys work in the common case where the same person signs out and back in. Rejected.
  - **D. By design, document only.** Leaves the cross-company publish open. Rejected.
- Recommendation: **A** now. Record B in `TODO.md` as a possible later item. Also downgrade the spec row 17.4 from "nothing shows" to "nothing can be published or run under the wrong account without the person choosing".

**17.5 / F2: an abandoned browser sign-in waits 300 s, then shows a generic error (S1).**
- Root cause: `services/auth_service.py:325` blocks on `done.wait(timeout=300)`. Nothing else can set `done`, and the code cannot see a closed browser tab. `LoginOverlay.tsx:47-54` disables the only button and offers no Cancel. When the wait times out, `RuntimeError("login_timeout_or_cancelled")` (`:329`) falls into `backend.py:791-796` and becomes code `internal_error`. `errorMessages.ts:183` turns that into "Something went wrong inside the app."
- The backend already runs every command on its own thread (`backend.py:822-824`), so a second command can cancel the wait.

**17.9 / F3: internal text in the two-step login card, and a ~3 min hang (S2?).**
- Hang: most likely caused by the tester's tooling, not the product. Playwright's `connect_over_cdp` asks Chromium to hold every new tab until each attached client lets it go (auto-attach with wait-for-debugger). The tester's Playwright client was attached to Studio's CDP endpoint and hung, so the "Checking sign-in" tab (`recorder/session.py:1202`) stayed paused at `about:blank` and never reached its marker. That matches the message exactly (`recorder/host_view.py:89`, 5 s per look, repeated across probes and attempts). Retest without tooling before treating it as a product bug.
- Product gap (real, low): `recorder/session.py:1228` (`learn_auth`) polls with no upper bound. Filed as a note only, not fixed here: an early return would leave the recorder thread mid-check.
- Wording (real): `recorder/session.py:1174` puts the raw exception into the reason shown by `GroupAuthWizard.tsx:529`.

**17.7 (S3): internal wording.** `conxa_compile/auth_learning.py:346,349,352`. These `self_test` reasons go straight to the card ("against what was learned", "learned signals"). The ~35 s wait comes from the BUILD-98 (4) settle-and-retry across up to 3 addresses, each starting two private browsers. Shortening it would weaken that rule, so it is not touched here. The card already shows "Checking sign-in…".

**17.8 (S3): contradictory runtime message.** `runtime/app/browser.js:1738` builds "...expired mid-run. Call execute_skill again — ...". The auto-retry branch `runtime/app/server.js:2389-2392` prefixes that whole message to "you do not need to call execute_skill again".

**F4: spec path for 17.6 is wrong.** Studio files are `~/.conxa-build-studio*/data/groups/<id>/auth/<app>.json` (DPAPI). Runtime files are `<data>/cache/sessions/<workspace>__<app>_state.json` (AES-GCM). Fix the spec row; no code change.

**F5 (Discard leaves "Recording") and 17.10 (group is the sign-in unit, by design)** are out of scope. Add F5 to `TODO.md`.
