## Root causes and decisions (fixer, 2026-11-21, Opus)
- **F1 / 16.1 — finished run read back as "unknown".** `run_registry.recordResult` had exactly one caller: the background sign-in wait (`server.js::_detachUntilSignedIn`). An ordinary run leaves the registry through one of ~15 return paths plus the main `finally`, none of which recorded anything, so `status(run_id)` found nothing. Fix at the one place every run passes: `_handleTool` is now a thin wrapper for `execute_skill`/`execute_sequence` that gives the run its id up front (`_run_id`) and, after the call, records the outcome through `run_registry.recordCallResult`. Rules: recorded only when the answer showed that run_id or the call continues a named run in the background (a refusal before the run started never shows an id); never for a hand-off to a sign-in wait (`_meta["conxa/awaiting_auth"]`, recorded later by whoever finishes the wait). Outcome: `completed` (Done / Done, please check / Submitted), `paused` (new: span, popup fork, hand-over, proof wait, test guard), `cancelled`, else `failed`. The sign-in-wait path no longer records its own copy (the wrapper does), which also fixes it calling a paused resumed run "failed". Decision: `paused` is a new state, so Execute's run follower (`conxa-execute/app/electron/run_follow.js`) now treats it as terminal (it would otherwise poll forever); its history shows it under "failed" via the existing fallback, same as before.
- **F2 / 16.11 — refused key silent.** `tracker.js` treated a 401 like any 4xx (drop, log `tracking_http_failed` with no status) and nothing reached the agent. `sync.js` already kept skills on a 401/403 (fetchJSON rejects non-200) but also only logged it. New `access_refused.js` (in-memory, per workspace): tracker and sync mark a workspace on 401/403 and clear it on 2xx; other statuses (offline, 5xx, 429) change nothing. `server.js` then adds one plain sentence to every run answer for that workspace and a `notice` to `list_skills` (works even when the workspace lists no skills): "Conxa could not confirm this computer's access: the key in this installation was not accepted. The workflows already installed still run, but updates and run reports cannot get through. To fix it, ask whoever gave you these workflows for a new installer and run it." The run's own outcome is unchanged ("Done." stays Done). `tracking_http_failed` now logs `status`.
- **F3 — bogus sync token dropped every skill: dev-only, prod safe.** Proof: `skillpack_update_routes.py::_verify_sync_token` skips the check only when `settings.auth_required` is false; prod sets `SKILL_AUTH_REQUIRED=true` (`conxa-cloud/render.yaml:22`) and `config.py` (~line 666) refuses to boot with `CONXA_ENV=prod` and auth off. In prod a wrong or revoked token is 401 `invalid_sync_token` / `sync_token_not_configured` (covered by `test_llm_proxy_and_publish.py:394`), and the runtime's `fetchJSON` rejects any non-200, so `sync.js` returns before touching `pack.json`. A real, authenticated empty list means the vendor removed every skill, so applying it is intended (files stay on disk; only `pack.skills` changes). Real hole found and closed: a **304** resolved as `{files: []}` (and any 200 body without a `skills` array) read as "no skills" and emptied `pack.skills`. `sync.js` now keeps the installed list unless the answer holds a real `skills` array.
- **16.9 older-app-layer half — note only, no test.** The prediction is about app layers older than the branch handlers (commit 45896e7, 2026-07-09). `required_capabilities` refusal (server.js) cannot help there: the capabilities mechanism itself arrived later (7030be60, 2026-10-18), so every layer that reads `required_capabilities` already runs branch bodies, and `required_runtime` compares the host exe, not the app layer. Old-layer behaviour lives in old code and cannot be unit-tested from this tree; it needs an old app-layer artifact. Left open as before.
- Not fixed (out of scope, noted): F4 (1-based step words vs 0-based `resume_from`), F5 (spec wording), F6 (input descriptions), O3 (recovery handoff text on scheduled runs).
