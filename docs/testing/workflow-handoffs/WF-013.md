## Requirements and expected outcomes
- "AI Review" no longer exists as a step: it was absorbed into the **agent span** (TRD 11.7, Engine v2 C4, 2026-11-06). The Add step menu offers only "Agent span". An AI Review is an agent span with no allowed actions and an answer schema ("One choice from a list"). A later step reads the answer as `{{<output_name>_<field>}}` (so `{{article_category_choice}}`, not `{{article_category}}` as in the spec).
- Only the span may spend tokens. Every other step must be zero-LLM.
- A destructive step must not directly follow a free-form span (and a span must not directly precede one). `destructive_step_cannot_directly_follow_agent_span`.
- Span clicks that look irreversible wait for a person; the agent picks numbered actions (`candidate_index`), never selectors.
- Spans fail closed in dry, scheduled, loop, called runs. Manifest says `uses_agent: true`.

## Other findings (UI/UX and product)
- **F-A (S1) Human Edit cannot save an answer on an agent span.** Open an agent span, pick "One choice from a list" (or Custom), type the JSON, Save step: nothing happens, no message, "1 unsaved" stays. Cause found with the debugger: the form submit throws `Cannot read properties of undefined (reading 'trim')` on `agent_span_answer_json` and the error is swallowed. Picking a preset also leaves the JSON box empty. Workaround used: ask the chat Copilot, then Apply (`Change the agent span answer schema`). This blocks the spec's "AI Review" setup for a non-chat user. Repro: Human Edit, new Agent span, set answer preset, type JSON, Save step.
- **F-B (S2) A span's answer is also asked as a required run input.** After `{{article_category_choice}}` was typed into Full Name, Studio registered `article_category_choice` as a text input; the test card shows "Article category choice, Text, required" and "Test inputs" shows what the person typed although the AI answer replaces it. The result card also says `article_category: [object Object]`.
- **F-C (S2) Chat reply and apply do not match.** Chat said "if no usable answer arrives ... the workflow keeps going" but the proposal left "If a usable answer never arrives" at "Stop the run" (default value stored, on_failure still abort). Leftover `option_a/option_b` field stayed in the schema until a second chat round.
- **F-D (S2) "Keep the AI helper off" label is confusing**: a ticked box means dry-run/no AI; for workflows with an AI step it is greyed and says "Turned off automatically — this workflow has 1 AI step, which need the AI helper" (grammar, and the box is unticked, i.e. the opposite of what the text says).
- **F-E (S3) Test screen**: "Step 12 of 10", "Step 6 of 5" progress; each span lists twice in the steps list; the agent giving up is shown as "Something went wrong at this step" (chat knows the real reason: "the agent gave up because it couldn't confirm the delete with the person"). The Studio stand-in agent gives up on a delete goal about 90% of the time, so a person testing a delete span mostly sees a failure.
- **F-F (S3) Jargon on plain screens**: "Agent span", "Change the agent span answer schema on step 5", Remove-step dialog says "removes the step from the skill package". The step list shows the title "A person confirms before the next step" for any new span.
- **F-G (S2, outside the spec) Submit click fails verification on a plain demoqa form.** `Verification failed: state_changed` after the real Submit succeeded, only when the span is in the workflow (runs 1-3); not isolated whether the span causes it. The recovery log shows `destructive_recovery_halted`.
- **F-H (S3) Clarify** asked "Should we ask for approval before clicking Save note?" for a plain Save click and listed raw-ish sentence "The recording starts with one record already open."
- Stray keystrokes: `tools/osinput.ps1` picks the first "Conxa Build Studio" window; another Studio (pid 8972, user-data `Conxa-Dev-i2`) was running. For my CDP window (pid 5968) I used `tools/osinput13.ps1` / `rec13.mjs`. Early on a few OS keystrokes may have gone into the other window.

## Root causes and decisions (fixer, 2026-11-20)
- **F1 / 13.1 (S0).** The order rule lived only in `patch_gate.validate_editor_patch` (a patched step vs its neighbours) and in `insert_step_after`. `reorder_steps`, `delete_step_at` and `replace_step_range` (splice, flatten popup) never checked it; neither did the build or the runtime. The insert refusal was a bare `ValueError` the handler did not catch, hence "Something went wrong inside the app". Fix: one rule, `patch_gate.span_before_irreversible` / `check_step_order` (destructive = `_is_destructive`: the compiler's `consequence` label or `judged_irreversible`, unsure = cannot be undone; only a confirm-only span is exempt), runs on the resulting step list in every structural mutation. Handlers turn a refusal into one plain sentence (`patch_wording.SPAN_BEFORE_IRREVERSIBLE`, now also used for the two older codes), write nothing and push no undo entry. Chat `move_step` / `delete_step` / `insert_step` go through the same commands, so the batch rolls back with the same sentence. The build refuses such a document (also when a dropped unfinished step closes the gap). The runtime refuses such a pack before any step runs (`run.js::spanBeforeIrreversible`, telemetry `agent_span_before_irreversible`), and `errors.js` now keeps span refusals as the plain summary instead of "Something unexpected went wrong". The irreversible click INSIDE a span still needs the person's yes (unchanged, `agent_span.js`); the Studio Yes-path is now unit-tested.
- **F2 / 13.3 (S1) — owner decision needed.** TRD §11.7 defines no per-run cap on spans. `_MAX_PAUSES = 5` counts popup decisions only. `_MAX_AGENT_SPAN_ROUNDS = 100` is a per-TEST-RUN total of stand-in rounds across all spans (not per span), a loop guard. The spec's 5-pause cap belonged to the removed AI Review step. No cap was invented and the spec was not changed. **Recommendation:** change spec 13.3 to "7 spans in one Studio test: each runs within its own budget; a span that gives up shows the plain reason; the run never loops (100-round guard)". A per-run span cap would be a product decision (TRD + Studio + runtime). The give-up message is fixed: `failure_summary.py` now says "The AI agent gave up on this part: <why>." or ran out of actions/time, kept trying what is not allowed, or gave no usable answer.
- **F3 / F-A (S1).** Root cause: `components/ui/textarea.tsx` was a plain function component under React 18, which drops `ref`, so react-hook-form's `register()` never reached the element. Typed text read back `undefined` (the swallowed `.trim()` TypeError) and a preset set by `setValue` never showed. Fixed with `forwardRef` (same as `Input`); this also fixes the call-another-workflow text boxes. `onSubmit` no longer swallows an unexpected error silently. Bad JSON already gets "The expected answer must be valid JSON (an object)".
- **F4 / F-B (S2).** `reconcile_inputs_with_step_values` declared every `{{name}}` it saw, including the span's own answer. Fix: `run_produced_names` (span answer + `<name>_<field>`, extract / clipboard-read names) is never declared; the test card hides a stale declaration; the packager drops one. "[object Object]": `server.js` wrote object outputs with string interpolation; now JSON.
- **F5 (S2).** Fixed: the "Keep the AI helper off" note now says the helper has to stay on. Not fixed (chat-model behaviour, not cheap or clear-cut): the chat reply claiming "keeps going" while the proposal left `on_failure: abort`, and the leftover `option_a/option_b` enum after one chat round. Recommendation: the chat card for a span answer change should state `on_failure` from the validated fields (code-written), as other summaries do.
- **F6 / F-G (S2) — not a span defect.** The failing check was `state_changed` on Submit. It passes on a URL change, an interactive-count change, or a body-text length change of more than 20 characters (`assertions.js` `STATE_CHANGED_TEXT_LEN_TOLERANCE = 20`). With the span's answer "person" typed, demoqa's result box adds only "Name:person" (about 11 characters), so nothing counted as a change, while the required text check "Name:person" passed. The span only made the typed value short. This is a general limit of `state_changed` on small results. Not changed here (proof/witness rules, risky). Recommendation (TODO): when a required text check on the same step proves the result, the compiler should not also make `state_changed` required.
- **F7 (S3).** Fixed: span title in the step list (`clarify._action_title`: confirm-only = "A person confirms before the next step", otherwise "The AI agent does a part on its own"); new span goal blank (`default_action_value`), so Save asks for it and the build drops an unwritten one with its warning (13.2 now reachable); Add step label "AI agent does a part"; the test card lists a resumed step once (no "Step 12 of 10"); Remove dialog wording. Skipped: F-H clarify asking about approval on a plain "Save note" (that is the model's irreversibility judgement; unsure = ask is the design); the "Change the agent span answer schema on step N" chat card wording.
- **13.2 / 13.5 / 13.6 at code level.** 13.2: a new span has no goal; the build drops it with "Step N: the agent step has no goal yet…" (test). 13.5 Yes-path: Studio resends the click with `user_confirmed: true` only after the person's yes; a no ends the test with nothing pressed (test). 13.6: the runtime refuses a span inside a loop (`agent_span_inside_loop`, new runtime test); dry run was already covered.

## Round 2 root causes/decisions (fixer, 2026-11-20)
- **G1 / 13.3 (S1) — owner decided: a 5-span cap.** One rule in one place, the runtime (`run.js`, `MAX_AGENT_SPANS_PER_RUN = 5`), so a Studio test (which runs the runtime) and a real run behave the same. Spans run only at the top level and once each (a span in a loop, option or called workflow fails closed before it would count), so the count is the span's place among the plan's free spans; resumes do not reset it and a caller cannot reset it through inputs. The free span over the limit never starts: `step_fail` `agent_span_limit`, plain sentence "This workflow uses the AI agent more than 5 times in one run. Conxa stopped here so it doesn't run away. Remove or merge some of the parts the AI agent does on its own." Studio's card reads the same (`failure_summary.py`). **Confirm-only spans do NOT count** (a person's yes, no agent work, and Clarify inserts them on its own); a confirm-only question after five free spans is still asked. Also: `stepFailure` dropped `agentSpanRefused`, so every span refusal (limit, loop, no agent, before-irreversible) could be parked for a Tier B recovery round; it is now kept and such a stop is never parked. Build/save does not refuse (a warning at test start instead, cheap and consistent: the test already builds and the build log was invisible). Python mirror `patch_gate.MAX_AGENT_SPANS_PER_RUN`, a test asserts both numbers agree.
- **G2 / F6 (S2) — root cause in the runtime witness.** The compiler synthesizes a required `state_changed` only when the step had no required check at compile time (`build.py::_build_assertions`); the `done_when` answer later makes the "Name:person" text check required, so the step carries both. `state_changed` counts only URL, element count or a text delta > 20 characters, so a short result failed it while the required text check proved the step with `fresh: true` (words absent before, present now). Fix (`assertions.js::verifyStep`): `state_changed` is evaluated last; when a required check already answered yes with `fresh: true`, the page did change, so it answers yes (`proven_by: "fresh_check"`) without polling. Words that were already on the page are not fresh, so `state_changed` still decides then: the witness rule holds, nothing rests on "the step ran". Not changed: the compiler/clarify (a compiler-side demotion would also drop the check when the text was already on the page).
- **G3 / 13.2 (S2).** The dropped-step warnings only ever reached the build log. Before a test, the chat now posts one plain message when a span has no goal ("One part the AI agent does on its own has no goal yet, so it is left out of this test. Open it in Human Edit…") and when the workflow has more free spans than the limit (`test_flow.py::_agent_span_notice`, counted by `skill_package_builder_saved_skill.agent_span_counts`, the same test the build uses). Not changed: Save on an untouched blank span still says "Nothing changed".
- **G4 (S3).** Fixed: Human Edit's default description of a span is the plain title ("Step 7: The AI agent does a part on its own", `describe.py` reuses `clarify._action_title`). Fixed: ending a test after allowing the agent's irreversible click says "Only what you allowed was done; nothing more was sent" / log "Nothing more was sent" (`_drive_runtime_pauses` carries `after_confirmed`; result + card field).
