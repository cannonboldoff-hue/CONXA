## Root causes and decisions
- **12.5b S0: chat can propose and apply a change to a step's page address.** Evidence is the applied diff above. `ADDRESS_KEYS` in `conxa-builder/python/conxa_compile/editor/capability_manifest.py` lists `action` but a navigate step also carries a top-level `url`; chat offered `url`, and the apply wrote `url`, `action.url` and `signals.context.page_url`. Not fixed by tester (product code). Route to BUILD-26.
- 12.3 is unreliable: the same request got a card on one wording and a refusal on two others, and after an Undo the model remembered the undone change and refused to re-offer it ("To get it back, use Human Edit"). Severity S3 (honest refusal, never a wrong change).

### Fixer (2026-11-20)
- **F1 (12.5b, S0) root cause: two holes, one at each end.** (a) `url` was a deliberate chat-editable field for navigate steps: `NAVIGATE_ALLOWED_KEYS` holds `url`, `ADDRESS_KEYS` did not, so `editable_fields("navigate")` offered it (the copilot prompt even listed `url` as an example field, TRD said "`url` ... editable", and `test_copilot_chat_edits.py` asserted it). (b) The after-apply guard `_keep_address_keys` explicitly let `url` change and re-synced its shadows `action.url` / `signals.context.page_url` to it, and could not have caught it anyway: an element-less step's `step_key` is hashed from its `url`, so a moved address also hid the step from the guard's key lookup. **Fix, one gate:** `url` joins `ADDRESS_KEYS`; new `capability_manifest.chat_may_write(kind, patch)` is an allow-list over every leaf a chat patch writes (so `URL`, `action.url`, `{"action": {"url"}}`, `signals.context.page_url`, `page_url`, `start_url`, `target`, mixed `{"intent", "url"}` all fail). It runs at card creation (`gate_proposals`) and again at apply (`handlers/copilot.py::_refuse_address_edit` on `patch_step`, `insert_step` and `body_insert_step` fields), so a stale card or crafted payload is refused with a plain message pointing to Human Edit (`ADDRESS_REFUSAL`, code `chat_cannot_repoint`). A new step whose fields ask for an address gets no card at all (`_names_an_address`), rather than a card that silently drops the address. `_keep_address_keys` now guards `url` too, keeps a change only when code templated part of the address into an input (`_templated_from`, the sanctioned `parameterize` path), and pairs an element-less step whose key moved with the step at the same index and action. Prompts: `url` removed from the example field list, "page address" added to the never-propose list and the Studio rules. No renderer mirror of `ADDRESS_KEYS` exists (checked `lib/actions.ts` and `src/`), so no drift.
- **F2 (12.7) not built: needs an owner decision.** The old floating copilot had edit-and-resend and "new session" (UI-UX-Brief, TRD "Sessions"); it was replaced by the per-workflow thread (`conversation/thread_store.py`), an append-only timeline that also carries question cards, test results and applied-change cards with Undo. No thread archive or truncate exists; cutting it would orphan applied/undoable cards and could hide open questions (which must always be answered). Logged as BUILD-114 (1) with a recommendation: "New conversation" = a divider that resets the model's context while keeping everything visible; "Edit and resend" only for the person's last message when no change card followed it. Spec unchanged.
- **F3 (S3).** Card titles and summaries use plain words (`copilot_proposals.field_words`: "Change the step's description", "Make the text in step 3 come from a run input"); "Show exact change" now shows `Field: <raw name>` and labelled Before / After. Before the first reply words arrive the chat shows "Working on a reply · N s" instead of a bare "…". **12.3 flakiness was a clear defect:** the ledger for the note workflow shows every failed wording as `gate_refused: structural`: the model (as its prompt says) used `parameterize`, whose two code rewrites only cover page addresses, record ids and clicked labels, so typed text was dropped. `parameterize` on text a person typed now becomes the same `value` field edit Human Edit makes (`_typed_value_edits`). Skipped: the "landmarks" jargon is the runtime's own drift warning (`runtime/app/run.js`), already a false alarm under BUILD-90; rewording it belongs with that fix (BUILD-114 (2)). Skipped: the model remembering an undone change (BUILD-114 (3)), and button names Apply/Dismiss vs spec's Accept/Reject (wording only).

## 12.7 build (2026-11-20, owner decision: minimal version)
**Root cause / decision.** The workflow thread is one append-only file that also holds questions, test results and undoable change cards, so cutting or archiving it could orphan a card or hide a question that must be answered. Built the BUILD-114 (1) recommendation:
- **New conversation** = a `new_conversation` divider (header button in Human Edit's Conversation, shown once something was said since the last divider; backend refuses an empty one). The model's turns and rolling summary start after the last divider (`thread_store.conversation_start`); nothing is removed, and every open card above it still rides in the context pack, stays visible (the unanswered question stays pinned above the composer) and stays answerable. Lifecycle, `expire_stale_cards` and the question rules read the folded thread exactly as before (dividers are just items).
- **Edit and resend** = `thread_turn{replaces: <id of last user message>}`. Allowed only when every raw line after that message is a plain reply or a summary (`thread_store.editable_message`): any card, card revision (a card answered/undone after it), divider, event, hidden message or reply to a command Conxa acted on (`routed`) blocks it, so nothing can be orphaned. One `retract{ids}` line removes the message and its replies from the folded view (the file keeps them); then the new text runs as a normal turn (one new reply). Refused with a plain message; the renderer shows "Edit" only on that one message (`lib/thread.ts::editableMessageId`, same rule) and never while a reply is being written.
- **Plain-language chat path skipped:** "start a new conversation" is not a lifecycle action (`actions.py` + `derive_lifecycle.allowed_actions` + renderer `lib/actions.ts` mirror + a flow command), so it is not trivial; the button is the path. "Edit my last message" by chat makes no sense (the request itself would be a newer message).
- **S3 honesty fixes:** an unclicked "Open Human Edit" link is no longer counted as an open card in the model's context (`INFO_CARDS` gains `action_link`), the reply is told the link is "a button, not a card", and the link reads "Open step N in Human Edit" instead of "point step N at a new element".
