## Failures / repro

**F-1 (9.1, S1) A radio group cannot be replayed.** Repro: demoqa /automation-practice-form, record First name, Last name, Email, click Gender "Female", Mobile, date, Submit. Compile, answer all, press Test (even with the recorded value "Female" and the ask-before box off). Fails at "Choose the student's gender": "Couldn't tell which of several matching elements to use." Cause seen in the package: `handler_hints.choice.options[*].selector` is `input[name="gender"]` for all three options. Suspected area: the choice-option selector builder (recorder `bridge.js` `buildChoiceContext` / compiler choice collapse) and `runtime/app/handlers.js::set_radio` (`option.selector || fallback`). Also: the answer "No, always Female" to the follow-up question did not remove the gender input (version 3 still listed 6 inputs).

**F-2 (9.2, S0 per spec) The meaning pass changes how a step acts.** Repro: record on /automation-practice-form (or /date-picker with the question left at the default): click the date box, click the "Previous Month" arrow, click a day. After compile the arrow step is `try_dismiss` with `branch.fallback_escape: true` (Escape would close the calendar if the arrow is missing) even though the model said "not optional". Recompile with and without the pass and diff (see 9.2 row). Suspected area: `compiler/second_opinion.py::_apply_one`, kind `suggest_optional`: it ignores the `proposed` value (a `false` verdict still converts). Also in C the person is asked "A small window popped up at 'Click Previous Month...'. Should it be closed whenever it shows up?" (a calendar arrow is not a window). Decision needed: the spec says address keys must be identical; CLAUDE.md allows `try_dismiss` branches from the pass. Either way the apply-when-false behaviour is a bug.

**F-3 (9.5, S1) The date step lands on the wrong month and year.** Repro: record /date-picker (open box, Previous Month, pick the 15th), answer "different every time", test with 2026-05-07 (or even the recorded 2026-10-15). The run lands on 12/xx/2026. Compiled hint: `handler_hints.date_picker.header` is the whole month-container (its text is "October 2026 January February March ..." because the page has month/year dropdowns) and no `month_select` / `year_select` was captured. Suspected area: date-picker hint capture (`compiler/date_picker.py` / recorder) and the nav loop in `runtime/app/handlers.js::_driveDatePickerGrid` (`monthDelta` on that text, `MAX_NAV_CLICKS` 24, no check that the month matches before clicking the day). Also compile leaves the open and arrow clicks as separate steps (3 steps, not 1).

**F-4 (S1, found on 9.4 fixture) A "send" button was judged reversible and re-clicked 7 times.** On D the review answer had no `effects` list, so "Click Send card" got `consequence: reversible` with no question. In the `?v=gone` run the failed text check made the runtime click it 7 times in 52 s (fixture log 03:08:22 to 03:09:02) and the failure card said "Nothing was saved or sent." Suspected area: `compiler/second_opinion.py` / `action_semantics.py::judged_irreversible` (no judgement should read as "unsure = cannot be undone"), and the retry-after-failed-check path. S2 part: the "Nothing was saved or sent" sentence was false here.

**F-5 (S3/S2 wording)**: input named "Due date" for a box labelled "Select Date" (C); "Done when ““date of birth”” appears" (doubled quotes, names an input as if it were screen text, B); the done-when question on C offered no suggestions and accepted an empty answer, so the test could only say "couldn't confirm".

**F-6 (S2) Personal typed values are shipped in the built package.** The author's typed name, email and addresses appear in `recovery.json` → `video_context.screen_after` (e.g. "The Email field now contains 'ravi.kumar1987@gmail.com'") in `~/.conxa-build-studio-dev/output/skill_package/wrk_local-plugin/skills/wf9-text-box-r2-16b3d0de/recovery.json`. ## Root cause + decision
Owner decisions: keep CLAUDE.md (the pass may write `try_dismiss` from a recorder-flagged popup hint); spec 9.2 reworded to "identical, except action/branch/recovery on a recorder-flagged popup the pass confirmed"; 9.3 gets a plain notice (not a listed archived step), spec reworded; an unsure effect counts as irreversible (more questions, intended).

- **F-2 / 9.2 (S0).** `second_opinion.py::_apply_one` (kind `suggest_optional`) never read `proposed`, and the validator only checked a recorder hint existed, so the model's own "false" still converted the calendar arrow to `try_dismiss`. Fix: validator drops a non-"true" verdict (`optional_declined`); `_apply_one` returns False unless `proposed` is "true".
- **F-1 / 9.1 (S1).** The recorder's `_selectorForElement` used `input[name="gender"]` for every radio (a name shared by the group). Fix: the stable selector is used only if it matches exactly one element in the root; otherwise the css path (which gives `#id` when present). Runtime, for already-recorded packages: new pure `choice.js::optionSelector` falls back to `input[type=radio|checkbox][name=group][value=v]` when another option carries the same selector; used by `set_radio` and `set_checkbox`. The "intercepted click" follow-up (hidden input under a label) was not needed in unit tests and is not live-verified; logged in TODO BUILD-111.
- **F-3 / 9.5 (S1).** Four causes. (a) `findCalendarRoot` widened only 6 ancestors, so the arrow and the day reached different outer nodes (react-datepicker popper/tab-loop wrappers), the run broke into two grids and the compiler could not fold "open, arrow, day" into one `date_pick`. Now walks up to 15, keeps the outermost calendar node and stops before an ancestor that holds an input the root lacks. (b) `_findCalendarHeader` took the first `[class*=month]` (the whole container with the dropdowns); now it ignores anything containing a `<select>` and takes the shortest text reading "Month YYYY". (c) The day record named no month/year dropdowns; it now records them and the compiler falls back to them. (d) Date format was read from the field before the pick; now from `field_display_value_after` first. (e) Runtime `parseHeader` took the first month in calendar order, not text order; fixed, and after navigating `_driveDatePickerGrid` reads the header and throws "The calendar shows X, not Y." instead of clicking a day on the wrong month (new pure `headerMatches`).
- **F-4 (S1).** `_validate_effects` returned [] when the model sent no effect for a step, so `judged_irreversible` returned None and the old word lists read "Send card" as reversible. Now every judged-action step without an answer gets `{reversible: None, confidence: 0.0, reason: "not judged"}`, which counts as cannot-be-undone. Verified the package builder did NOT carry that to the runtime (it only read `identity_bundle.destructive`, set before the judgement); `_copy_saved_common` now also sets `destructive: true` from `judged_irreversible` (the address is untouched). `cascade.js::guardDecision` now blocks (never re-dispatches) a destructive step that already acted and failed its check.
- **F-6 (S2).** `recovery.json` copied `video_context` raw; each field now goes through `app_graph/scrub.py::scrub_text` (200 chars). Residual in Security.md SG-25.
- **9.3 (S1).** `recorder/session.py::ignored_click_count()` counts `unrecorded_click` gaps; `handlers/session.py` returns `ignored_clicks` from stop; `handlers/workflow_flow.py::ignored_click_note` adds a plain sentence to the three post-recording messages. `capture_gap_count` (lost steps) is unchanged.
- **F-5 / F-7 (S3).** Date input fallback names `date` / `date_time` (added to the generic names the pass may rename); "Done when" no longer double-quotes an input name and says "the X you entered appears" for a bare input; `recompile_session.py` message names the working env pair. Offline-router fix and the 0.45 vs 0.315 mismatch are in TODO BUILD-111.
