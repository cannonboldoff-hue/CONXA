## Root causes and decisions (suspected layer only; nothing fixed)
- Large upload (S2): runtime `app/handlers.js` `upload` handler -> `locator.setInputFiles(..., {timeout: ACTION_TIMEOUT_MS})` where `ACTION_TIMEOUT_MS` is 2500 ms (`run_config.js`). In a host-panel run that call times out for files above a few MB; at 100/200 MB the step is recorded as "couldn't confirm" instead of failing, so the run goes on to press Upload with an empty box and blames the click. Suspect: fixed 2.5 s budget, plus the choose-files proof being only "couldn't confirm" when the box is empty (`validation.effect.kind` not `choose_files` strict). Also suspect the host panel's file hand-off (`host_browser`), since standalone Chromium is instant.
- Empty/stuck download (S2): `runtime/app/server.js` download listener -> `hostBrowser.saveDownload` returns an error string "HTTP 500" in a host-owned run, so `handlers.js` `download_observed` maps it to the generic branch `the download failed (...)` instead of the empty/timeout branches. Suspect layer: host `saveDownload` error mapping (`host_browser.js`).
- Wording (S3): Studio's headline for several different failures is the same "One of the values given for this test isn't one this step can use." (seen for the folder-to-single-input refusal, the empty download and the stuck download). Only the folder case is accurate.
- All "Find the cause" auto-replies after the failed upload tests guessed wrongly ("file_path was not supplied / file no longer exists"); they never saw the real error. They also spend LLM tokens without being asked.

## UI/UX notes (non-technical user)
- The Test inputs card for an upload says "I've put your recorded values in" but the file path box is empty. It is a plain text box; a person must type a full Windows path, and for a folder they must know to type the folder's path. No Browse button. The question during compile says "Which file should be uploaded?" even for a multi-file picker; nothing explains that a folder works for many files.
- "Whose uses it picks the file" wording differs between two recordings of the same kind ("No, whoever uses it picks the file" vs "A file I pick each time").
- The proof question offers the page's own count text ("Received 3 files: file-1.txt (52), ...") as a tick-box, which would wrongly fail with 20 files. Unticking it then showed "Keep at least one required outcome check" until a custom word was typed.
- Refusal of a folder for a single-file page: headline is vague, and the buttons offered ("Fix it myself in Human Edit", "Find the cause") do not help (the real fix is to give one file). A "landmarks missing" redesign warning is also shown (known BUILD-90 style false alarm).
- Stuck download: 2 min 07 s with only "Test running ... Step 3 of 3" and no hint that Studio is waiting for a download; message at the end does not mention time.
- Recording quirk: clicking a file input or link with mouse clicks through the automation was flaky in the Studio pane ("body intercepts pointer events"), keyboard activation worked. A real person's mouse was not tested. The native file picker opened pointed at an empty run folder, not the last chosen folder.
- Recording a keyboard-activated download produced eight steps with six "Press Tab until ..." steps. A non-technical person would not understand that list. (Artifact of my driver, but shows how keyboard recordings read.)

## Fixer (2026-11-20)

### Root causes
- **Large upload (14.8b).** Not the 2.5 s budget as such. `runtime/app/host_browser.js::acquire` called `chromium.connectOverCDP(cdp)` without `isLocal`, so Playwright treats the host browser as remote (`_isCollocatedWithServer = false`). For a remote browser `setInputFiles` reads every file into memory, base64-encodes it and pushes it through CDP (`playwright-core/lib/server/fileUploadUtils.js`), and refuses 50 MB or more outright ("Cannot transfer files larger than 50Mb to a browser not co-located with the server"). So 1 MB passed, 40 MB timed out at 2500 ms, 100/200 MB threw at once. A plain launched Chromium is co-located, which is why the tester's standalone check took 9 ms. Reproduced on a separate, isolated Electron (not the Studios): `isLocal=false` gives 1 MB 245 ms, 40 MB timeout, 200 MB refused; `isLocal=true` gives 1 MB 67 ms, 40 MB 19 ms, 200 MB 23 ms, and the page reads all 209,715,200 bytes back. With paths the attach time no longer grows with size, so no size-scaled timeout is needed.
- **Why the Upload press was blamed (100/200 MB).** The attach error went into recovery and came out "couldn't confirm, continue" (recovery log: 13 resolve retries, then `proof couldnt_confirm`). Likely `cascade.js::guardDecision` returning "recovered" because a check unrelated to the file box held. Not changed here (the attach no longer fails); logged as RT-19 (1).
- **0-byte and stuck download (14.8).** Studio's panel already fails with typed reasons (`empty: ...`, `timeout: ... did not finish in 120000ms`), and `browser_control.js` sends them as `500 {error}`. `host_browser.js::_controlPost` used `httpClient.postForBuffer`, which rejects any non-200 with a bare `HTTP 500` and drops the body, so `handlers.js` `download_observed` fell to its generic branch. Also the `timeout` prefix had no plain branch there, and Studio's headline (`failure_summary.py`) puts the `bad_input` sentence first ("One of the values given...") for any download failure.
- **2 min 07 s.** A defined limit: `CONXA_DOWNLOAD_WAIT_MS` (default 120000 ms, `runtime/app/run_config.js`), which on a host panel covers the transfer too (`browser_panel.js::saveDownload`), plus the earlier steps. Now written in `docs/TRD.md` (download lifecycle).
- **Auto "Find the cause" replies.** Not an invariant breach. It is Studio's "Find the cause when a test fails" setting (Settings, Testing; `autofix_enabled`, on by default), which only proposes and changes nothing until Apply. The "LLM only at Tier B" rule is about the runtime's recovery, not Studio's diagnosis. Its wrong guesses came from the swallowed attach error above. No change.

### Fix
- `runtime/app/host_browser.js`: `connectOverCDP(cdp, { isLocal: _isLoopback(cdp) })`; `_controlPost` relays the host's `{error}` text on a non-200 reply (falls back to `HTTP <status>`); `saveDownload` turns the channel's own "post timeout" (a host with no transfer limit, e.g. Execute's panel) into `timeout: ...`.
- `runtime/app/handlers.js` `download_observed`: a `timeout` reason reads "it did not finish downloading within 120 seconds"; the other time messages are in seconds, not ms.
- `conxa-builder/python/conxa_compile/conversation/failure_summary.py`: a download failure gets its own plain headline (empty or cut short / took too long / stopped before saved / no file started / couldn't be downloaded) ahead of the bad-input sentence. The folder-to-single-file refusal keeps the bad-input sentence.
