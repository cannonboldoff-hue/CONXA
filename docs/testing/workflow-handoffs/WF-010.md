Findings / cause hypotheses
- F1 (10.4, S1, root cause confirmed by code read): `handlers.js` wait_for_one_of calls `probePresent(page, option, inputs, 0)`; `pollPositive` -> `page_eval.js::withDeadline(fn, deadline=now, false)` races the real browser `count()` against a 0 ms timer, which always wins on a real page, so every option probe reads "absent". test_branch.js passes because mock pages resolve in microtasks. Effect: all wait_for_one_of arms (success->logout, error->nothing) are dead; non-required waits just burn the timeout (5 s). Fix: give the inner probe a small non-zero budget (or run it once without a deadline race).
- F2 (S2): hand-saved branch steps built in Human Edit UI: if_present Primary selector + nested click selector typed and "Save step" showed "saved" but the stored step kept empty selectors (disk showed empty); the Studio's real store is `data/kv/skills/<hash>.json`, `data/skills/*.json` is only a copy. Not fully reproduced (my UI path also went through the picker twice); unverified.
- F3 (S2): `if_present` probe counts a hidden-but-in-DOM element as present (`countOn` > 0), so #modal on a repeat visit is "present" and the body click runs against a hidden element (162 ms). Plain-language check only.
- F4 (S3): failed-step message on the Studio card differs from the runtime reason (10.13, 10.9) and can name the wrong step (10.7).

## Engineering round 1 plan
Read-only investigation, 2026-11-19. No recorder regression found: 0eaf4e70 and 4170a68f do not touch the capture path for either symptom.

**(a) /login typing + Login click = 0 actions. Verdict: BY DESIGN (harness picked a sign-in page), plus one plain-language gap.**
- Root cause: `conxa-builder/python/conxa_compile/recorder/session.py:2054-2069` drops every event whose page path is a sign-in page ("Signing in is never part of a workflow (auth lives in the saved session)"), and logs it to `login_drops.json`. `/login` matches `SIGN_IN_PAGE` in `packages/conxa-core/conxa_core/login_paths.py:19-21`; `LoginFlowTracker.is_login_step` at `recorder/frame_utils.py:241-249`. A password box also arms it (`session.py:2057`). Settled or not, every event on /login is dropped.
- It is not a bridge race: the Logout click on /secure after the driver's `goto` WAS recorded, so the bridge and binding survive Playwright-driven navigation. The /login submit click and both fields are dropped on purpose; the arrival on /login after Logout is kept as the click's result (`_mark_sign_in_arrival`, `session.py:259`).
- Gap: a recording that holds only sign-in steps ends with "No workflow actions were recorded." (`handlers/session.py:53-54`). A non-technical person gets no reason.
- Fix (small, optional): in `_empty_reason`, when the session has login drops, say "You only signed in. Signing in is saved separately, so it isn't part of a workflow. Sign in first, then record the steps after it." Needs `sess._login_drops` passed in (stop handler, `handlers/session.py:639-671`).
- Harness fix: type into a non-sign-in page for WF-010 (`docs/testing/fixtures/decision.html`, the-internet `/inputs` or `/forgot_password`). Do not use `/login`.

**(b) Click on the entry_ad `<p>Close</p>` = 0 actions. Verdict: by-design filter that is too narrow (product gap, owner decision).**
- Root cause: `recorder/bridge.js:2695-2700`: `resolveMeaningfulTarget` returns null, so the click becomes a `_gap` ("unrecorded_click", `session.py:1886-1890`) and the "clicked on parts of the page that aren't buttons" note (`handlers/workflow_flow.py:41-47`). `isInteractiveNode` (`bridge.js:431-461`) accepts a script-wired element only with `title`/`aria-label` AND `cursor:pointer` (the demoqa trash-icon rule, `bridge.js:449-459`). The page's markup: `<div class="modal-footer"><p>Close</p></div>`, jQuery `$('#modal .modal-footer').on('click', dismissedAd)`, CSS `#modal .modal-footer p { cursor: pointer }`; no title, role, tabindex or onclick attribute. WF-9 9.3 made the drop deliberate for blank space and headings; this `<p>` is neither.
- The note is also false here: it tells the person the click "does nothing" when it closed the popup.
- Proposed fix (one rule in `isInteractiveNode`, next to the titled-icon rule): accept an element with its OWN pointing hand (its computed `cursor` is `pointer` and its parent's is not, so an inherited cursor on a card's children never counts), short own visible text (1 to 40 characters), and no control holding it (same `closest(...)` check as line 455). Text-less pointer areas (the modal underlay) stay unrecorded.
- Do not touch the identity/descriptor contract: target choice is not part of `test_element_descriptor_agreement.py`. Add one line to `docs/TRD.md:1299` (interactive-node rules).

**CDP `Input.dispatchMouseEvent` (isTrusted:true, nothing captured).** The bridge has no input-source filter (no pointerType or sourceCapabilities check). The CDP probes most likely hit the two cases above. Unverified: re-check one CDP click on a real control (the "click here" link) before treating it as a separate bug.
