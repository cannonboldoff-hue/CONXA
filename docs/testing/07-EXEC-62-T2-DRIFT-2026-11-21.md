# EXEC-62 (DT15-7): the `t2` drift on `recovery-fixture.html`, re-run after the "Buy Now" unbinding (2026-11-21)

**Question.** The 2026-11-15 run failed `t2` because the compiler had tied the "Buy Now" click to a row named "Buy Now" (`05-DEV-TEST-RUN-REPORT-2026-11-15.md` §9, §10.2, §46). That row binding is gone now. With it gone, does the renamed button heal, and what does the kept `#checkout-btn` give?

**Short answer.** For `t2`, **yes, and recovery plays no part.** The `t2` button is renamed to "Purchase order", loses its test id and aria label, and keeps `id="checkout-btn"`. Primary resolution finds it through the compiled `#checkout-btn` signal. There are zero recovery events and zero tokens, the right button is clicked, and this holds at ceiling 2 and at ceiling 4. For a **true rename with no surviving id** (`d3`), **no**: nothing in Tier A finds it, and because a "Buy Now" click counts as irreversible, Tier B is withheld too. EXEC-28 still stands.

One more finding hides both answers on the fixture as it is. **Every run of today's compile fails at the click, the clean page included.** The fixture's visible change after the click is too small to count as proof for an irreversible click, so the run stops on "Verification failed: state_changed". It stops after the click has already reached the page. Identity is not the cause.

### How `#checkout-btn` wins on `t2`

The four name-based signals (testid, role "Buy Now", text "Buy Now", relational) each match 0 elements. `#checkout-btn` matches exactly one. That candidate scores **0.33** against the recorded fingerprint, which is below the 0.5 confidence threshold, because the name, text and testid all disagree. It is accepted only through the **trusted-contract rule** (`resolver.js::isContractSignal` / `contradicts`). A unique DOM id or test id is taken as identity unless the live element carries a *different* test id. The `t2` button has no test id at all, so nothing contradicts it. The uniqueness-margin rule still holds: one match gives margin 1, and `candidate[0]` is never picked blindly.

One consequence to keep in mind: if the drifted page had kept the id but given the button a **different** test id, the same signal would be refused and `t2` would fail like `d3`.

## Answer to EXEC-62

1. **The renamed `t2` button heals, at primary resolution, by the kept `#checkout-btn`.** No recovery tier is involved, there are zero tokens, and it is the same at ceiling 2 and 4. Runbook R1's expectation ("passes via `tier2_a11y`") is stale for this reason, exactly as EXEC-31 already says.
2. **A rename with no surviving id or test id does not heal** (`d3`). The Tier A a11y re-probe searches by the *recorded* name and finds nothing (EXEC-28, unchanged). On an irreversible click, Tier A skips that re-probe and Tier B is withheld at any ceiling. That stop is the intended safety rule, not a bug.
3. **On the fixture as checked in, today's compile cannot pass R0 or R1 at all.** The run stops after the click has reached the page, because the irreversible click's required "the page changed" check sees only about 11 new characters, under the 20-character tolerance (`assertions.js::STATE_CHANGED_TEXT_LEN_TOLERANCE`). The page sends no request, so the `send` contract has nothing to stand on either.

## Proposed follow-ups (not built)

- **A. The recovery fixture's click effect is too small to prove a purchase click (test fixture).** Make the target's click show a real confirmation line and send a data-changing request that the server answers 2xx. The existing `GET /__log` beacon does not count for the `send` contract, so the runbook's `:8099` server must also accept a POST. Then update runbook rows R0 and R1 and step 41 (`alternatives` no longer exists; R1 resolves at primary through `#checkout-btn`). This is small, but it changes what the runbook server must do, so it is not a one-line fixture edit and was not applied. The harness's `CONFIRMED=1` patch shows the shape.
- **B. The irreversible-step stop says "the recorded target could not be re-found" when the target *was* found and clicked** (`failure_response.js::haltReasonNoteText`, the `destructiveHalt` branch). In asis-t2 at ceiling 4, the page logged `t2:target` and only the proof failed, yet the agent was told the element could not be found. On a purchase that may already have gone through, the text should say the click was made and could not be confirmed, so nobody re-runs it blindly. This is a wording-only change in runtime source (not touched here: runtime ownership).
- **C. EXEC-31 is confirmed again; no new item is needed.** There is still no fixture variant that reaches the Tier 2 a11y heal. `d3` "undoable" shows the a11y re-probe running and missing, because it keys on the recorded name (EXEC-28).

A person's answer to the "can this be undone?" question would beat both; the "undoable" rows cover that case.
- The runtime ran from source, not the packed host exe. Resolution and cascade code are the same files the exe loads.
